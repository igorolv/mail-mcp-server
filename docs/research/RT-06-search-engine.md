## Кратко

- [предположение] Рекомендую Apache Lucene 10.5.2: BM25, морфология, фрагменты текста и
  векторный поиск доступны внутри JVM без отдельного сервера. Это предложение, не решение. [1–8]
- [док] Актуальная основная ветка — 10.x; выпуск 10.5.2 датирован 2026-10-04.
  Требование Java 21+ совместимо с запланированной Java 25 на уровне минимальной версии. [1–2]
- [код] В Lucene есть готовый `TopDocs.rrf`: вручную реализовывать обычное объединение
  результатов BM25 и kNN по обратным рангам не требуется. [6]
- [предположение] Начать с `RussianAnalyzer` / Snowball и отдельного английского поля.
  Главный риск — пропуски нерегулярных форм: `письмо → письм`, `писем → пис`. [9–12]
- [док] `russianmorphology` использует словарь АОТ и возвращает несколько разборов омонимов.
  Совместимость с Lucene 10 не подтверждена; README, POM и история расходятся. [13–15]
- [код] Hunspell со словарём LibreOffice — запасной кандидат, но словарь орфографии
  не гарантирует объединения всех форм: `писем` записано отдельно от `письмо/K`. [16–18]
- [док] FTS5 имеет BM25, но встроенного русского стеммера нет. Интерфейс токенизаторов — C;
  xerial загружает расширения, однако готового Java-интерфейса регистрации не найдено. [21–23]
- [предположение] SQLite FTS5 + `sqlite-vec` оставить альтернативой: потребуются поставка
  нативного расширения и дополнительная обработка русского текста. [21–26]
- [предположение] Для 100 000 писем важнее объём извлечённого текста и число фрагментов,
  чем число писем. Достоверных цифр размера индекса и памяти без корпуса нет; см. В1.

## Ответы на вопросы

### В1. Apache Lucene: возможности, обновления и ресурсы

**Версия и BM25.** [док] Официальная страница загрузки на дату исследования указывает
10.5.2. Объявление выпуска отдельно отмечает исправление полноты HNSW-поиска при редких
постоянных удалениях — существенный случай для почтового индекса. [1]

[док] BM25 — стандартная функция релевантности. У `BM25Similarity` параметры по умолчанию
`k1=1.2`, `b=0.75`; их можно настраивать. Повышение веса темы относительно тела — настройка
запроса/полей, а не причина менять движок. Последнее — рекомендация. [3]

**Векторы.** [док] `KnnFloatVectorField` содержит один плотный вектор на документ для данного
поля; `KnnFloatVectorQuery` ищет ближайшие документы и принимает фильтр. При достаточно
узком фильтре реализация может перейти от приближённого поиска к точному. [4–5]

[предположение] Если вложение разделено на десять смысловых фрагментов, хранить их как десять
поисковых документов с общим идентификатором вложения. Несколько векторов нельзя считать
просто несколькими значениями одного `KnnFloatVectorField`. [4]

[док] HNSW доступен через форматы векторного индекса. В `Lucene104HnswScalarQuantizedVectorsFormat`
есть настройка связности графа и очереди построения; API формата помечен экспериментальным. [7]

[док] В `ScalarEncoding` перечислены 1, 2, 4, 7 и 8 бит на компоненту; для 1/2 бит предусмотрена
асимметричная обработка с 4-битным запросом. Это возможности конкретных форматов, а не
автоматическая настройка любого векторного поля. [7–8]

[предположение] Для первого варианта векторов оставить исходную точность, затем сравнивать
квантование по полноте выдачи. Размер квантованных компонент не равен размеру всего индекса:
есть граф, метаданные, а формат может сохранять исходные векторы. [7–8]

**BM25 + kNN.** [код] `TopDocs.rrf(topN, k, hits)` суммирует `1/(k+rank)` для документа,
где ранги начинаются с 1. Параметр `k` здесь — константа сглаживания, а не число соседей.
Идентичность результата определяется парой `(shardIndex, doc)`. [6]

[предположение] Выполнять оба поиска на одном захваченном `IndexSearcher`, с одинаковыми
фильтрами соединения/доступности; объединять достаточно широкие списки кандидатов.
Пропущенный обоими поисками документ RRF не восстановит. Для разных индексов или разных
снимков сначала сопоставлять результаты по собственным стабильным ключам. [6, 29]

[док] В 10.5 появились также `BayesianScoreQuery` и `LogOddsFusionQuery` для вероятностного
объединения оценок. [1] [предположение] Для начала RRF проще: не требует подгонять сопоставимые
численные оценки BM25 и векторного сходства. Простое сложение этих оценок не рекомендую. [6]

**Фрагменты и подсветка.** [док] Модуль `lucene-highlighter`, класс `UnifiedHighlighter`,
получает смещения из postings, term vectors либо повторного анализа исходного текста.
Это три способа получить позиции совпадений, с разной ценой хранения и чтения. [19]

[предположение] Хранить извлечённый текст вне индекса как восстанавливаемый источник;
для больших полей рассмотреть позиции со смещениями, для коротких — повторный анализ.
Сам по себе векторный результат не содержит лексического совпадения: ему нужен сохранённый
фрагмент, а не обещание подсветить слова запроса. [4, 19]

**Поиск вскоре после записи.** [док] `SearcherManager` безопасно разделяет поисковые объекты
между потоками. Документация рекомендует обновлять их через `maybeRefresh()` в фоне.
Старый читатель продолжает работать со своим снимком. [29–30]

[док] `IndexWriter.updateDocument` заменяет документ удалением старого и добавлением нового;
есть `deleteDocuments`, изменения сначала могут находиться в буферах. `commit()` фиксирует
состояние на диске. [30] [предположение] Обновление читателя для видимости и фиксацию для
восстановления после сбоя следует планировать отдельно.

**Размер и память.** [док] Lucene не задаёт универсальных требований: они зависят от размеров
документов, числа результатов и других настроек. `MMapDirectory` отображает файлы в адресное
пространство; размер отображения не означает такой же размер Java heap. [2, 31]

[предположение] Следующие числа — арифметические сценарии для планирования, не измерения
Lucene и не обещание производительности:

| Сценарий | Расчёт | Что не включено |
|---|---|---|
| 100 000 писем, по 20 КБ извлечённого текста | Около 2 ГБ текста | Вложения сверх этой оценки, MIME, копии в индексе |
| 100 000 векторов по 384 float32 | 153,6 МБ, примерно 146 МиБ | HNSW, идентификаторы, сегменты, текст |
| 1 000 000 фрагментов по 384 float32 | 1,536 ГБ, примерно 1,43 ГиБ | То же; это уже другой масштаб, чем 100 000 писем |
| 100 000 векторов по 768 float32 | 307,2 МБ, примерно 293 МиБ | То же |
| 384 компоненты, 4 бита вместо 32 | Теоретически 8 раз меньше для самих компонент | Исходные векторы и остальные структуры |

[предположение] Планировать дисковый индекс и ограниченный буфер записи, не загрузку всей
почты в heap. Учитывать отдельно heap, физическую память отображённых файлов, кэш ОС,
извлечение вложений и модель эмбеддингов. На перестроение нужен второй индекс и запас для
слияния сегментов; точный коэффициент не установлен. [30–32]

### В2. Русская морфология, смешанный текст, адреса и имена файлов

[код] В Lucene 10.5.2 `RussianAnalyzer` строит цепочку `StandardTokenizer → LowerCaseFilter →
StopFilter → SetKeywordMarkerFilter` при наличии исключений, затем `SnowballFilter(RussianStemmer)`.
Список стоп-слов и исключения стемминга можно передать извне. [9]

[док] Snowball удаляет окончания по правилам; это не словарь нормальных форм.
Авторы прямо предупреждают, что нерегулярное склонение даёт разные основы.
Замена `ё → е` включена в реализацию Snowball с 2018-03-16. [10]

[предположение] Для писем риск проявляется в двух направлениях: формы одного слова остаются
разными либо разные слова получают одну основу. Термины, аббревиатуры, номера договоров и
собственные имена стоит дополнительно сохранять в полях без стемминга. [9–12]

[док] `russianmorphology` / `LuceneMorphology` использует словарь АОТ, эвристики неизвестных
слов и несколько разборов омонимов. README рекомендует переиспользовать объект морфологии
из-за объёма его данных. [13]

[код] Доступный POM указывает Lucene 9.3.0 / morphology 1.5, README — Lucene 9.9 / 1.6.
Доступная история показывает верхний коммит `71af7f6` от 2022-09-28. Это несогласованные
представления источников; считать дату последней разработки установленной нельзя. [13–15]

[предположение] Не подключать старый Lucene транзитивно рядом с 10.x. Перед выбором
словарного варианта проверить конкретный коммит, сборку и адаптер на 10.5.2. Сам факт наличия
Java-библиотеки не доказывает совместимость её фильтров с новой основной версией. [14]

[док] `HunspellStemFilter` в Lucene применяет словарь и правила аффиксов, может выдавать все
основы или только самую длинную. Это Java-реализация Lucene; нативный `libhunspell` для этого
пути не нужен. Словари `.dic` / `.aff` поставляются отдельно. [16]

[предположение] Не приравнивать Hunspell к полноценной лемматизации: качество зависит от
конкретного словаря. Слово, отдельно перечисленное для проверки орфографии, может остаться
отдельным поисковым термином вместо объединения с другой формой. [16–18]

**Примеры без исполнения.** Ниже результаты из опубликованных данных, правил и описания.
`[код]` означает чтение файла, а не запуск теста; ручные выводы явно помечены.

| Вариант | Короткий пример | Основание и предел проверки |
|---|---|---|
| Snowball | `письмо / письма → письм` | [код] Парные строки `voc.txt` / `output.txt` 27694, 27704, нумерация от 0. [11–12] |
| Snowball | `писем → пис`, поэтому не совпадает с `письмо` | [код] Строка 27684 в тех же файлах. [11–12] |
| Snowball | `план / плана / планами → план` | [код] Строки 27788–27790 тех же файлов. [11–12] |
| Snowball | `договор / договора / договорами → договор` | [предположение] Ручной вывод по правилам снятия `а`/`ами`; готовый тест этой тройки не найден. [10] |
| LuceneMorphology | `вина → вино, вина` | [док] Явный пример омонимии в README; контекстное значение не выбирается. [13] |
| LuceneMorphology | `ёлка / елка` рассматриваются одинаково по `ё/е` | [предположение] Применение прямо заявленного правила README; точный список лемм не проверен. [13] |
| LuceneMorphology | `наибольший` рассматривается как отдельное слово | [док] Ограничение из README; объединение с `большой` не обещано. [13] |
| Hunspell + LibreOffice ru_RU | `договорами → договор` | [код] `договор/K`, правило `SFX K 0 ами`; ручное чтение допустимого разбора. [17–18] |
| Hunspell + LibreOffice ru_RU | `письмами → письмо` | [код] `письмо/K`, правило `SFX K о ами`; ручное чтение разбора. [17–18] |
| Hunspell + LibreOffice ru_RU | `писем → писем` | [код] Самостоятельная запись `писем`; правило `письмо → писем` не найдено. Полный вывод фильтра проверить отдельно. [17–18] |
| Hunspell + LibreOffice ru_RU | `машины → машина` | [код] `машина/I`, правило `SFX I а ы`; указан допустимый разбор, не полный список. [17–18] |
| FTS5 unicode61 | `договор / договора / договорами` остаются разными | [код] Нормализация регистра без русского стемминга. [43] |
| FTS5 unicode61 | `письмо / писем` остаются разными | [код] Нет словарного приведения форм. [43] |
| FTS5 porter | `план / планами` не получает гарантированного русского объединения | [док] Porter рассчитан на английский; это не русский стеммер. [21] |

[предположение] Эти примеры показывают механизмы и ограничения, но не доказывают сравнительное
качество на деловой переписке. Для LuceneMorphology подтверждены только описанные случаи;
полные леммы договоров и писем остаются неизвестными, а не подразумеваются правильными.

**Русский и английский в одном исходном поле.** [код] Штатная цепочка `RussianAnalyzer`
не содержит английского стеммера. [9] [предположение] Для MVP копировать исходный текст в
два индексных поля: русское с `RussianAnalyzer`, английское с `EnglishAnalyzer`; искать по
обоим с объединением результатов. Это проще, чем собственное определение языка каждого слова. [45]

[предположение] Цена двух полей — дополнительные postings и настройка весов. Не складывать
безусловно две оценки одного текста: можно выбирать лучший результат поля. Альтернатива —
своя цепочка с разветвлением по алфавиту, но её обработку смешанных слов придётся проверить.
Это относится к теме, телу, именам участников и тексту вложений, не к полным адресам. [9, 20]

**Адреса и файлы.** [док] `UAX29URLEmailTokenizer` распознаёт адреса/URL по отдельным правилам.
`WordDelimiterGraphFilter` умеет разбивать технические имена и сохранять исходный токен;
документация предупреждает о токенизаторах, заранее теряющих разделители. [20]

[предположение] Полный адрес `user@example.com` хранить отдельным точным термином с явно
выбранной нормализацией; имя человека — анализируемым текстом. Для файла сохранять полное
имя и расширение отдельно, а составные части (`договор`, `2026`, `pdf`) — для полнотекстового
поиска. Сначала разбить имя, затем применять языковые фильтры; не стеммить полный адрес.

### В3. SQLite FTS5 и sqlite-vec из Java

[док] `bm25()` возвращает меньшую оценку для лучшего совпадения; стандартная сортировка —
по возрастанию. Есть веса колонок, `highlight()` и `snippet()`. Встроенные токенизаторы:
`unicode61`, `ascii`, английский `porter`, `trigram`; последний ищет подстроки, не леммы. [21]

[док] Пользовательский токенизатор регистрируется через C-интерфейс `fts5_api` /
`xCreateTokenizer`. [44] [код] В просмотренном `NativeDB` xerial есть загрузка расширений,
но интерфейс регистрации FTS5-токенизатора не найден. Java SQL-функция не заменяет этот API. [22–23]

| Путь для русской морфологии | Вывод для Java-сервера |
|---|---|
| C-расширение с токенизатором | [предположение] Рабочий архитектурный путь через загрузку библиотеки, но сборки для каждой ОС/архитектуры становятся нашей обязанностью. [22–23, 44] |
| Собственный JNI/FFM-мост к C API | [предположение] Возможен, но выходит за рамки обычного JDBC и не проверен в этой задаче. [22, 44] |
| Предварительные леммы/основы в Java | [предположение] Индексировать преобразованный текст и так же преобразовывать запрос; отдельно хранить оригинал и соответствие смещений. [43–44] |

[предположение] Последний вариант позволяет избежать собственного нативного токенизатора,
но ухудшает простоту фрагментов и фразового поиска: длины слов меняются, несколько лемм в
одной позиции нельзя без потерь представить обычной строкой. Это существенная цена обхода.

[код] xerial включает FTS5 и поддерживает `SQLiteConfig.enableLoadExtension(true)` с SQL
`load_extension`. Пользовательские токенизаторы и другие сторонние расширения не входят в JAR. [23]

[док] `sqlite-vec` — расширение на C без внешних зависимостей; хранит float32, int8 и бинарные
векторы. Оно находится до версии 1.0 и предупреждает о несовместимых изменениях. На странице
документации показана версия `0.1.10-alpha.4`; это не основание считать её стабильным выпуском. [24]

[док] Для kNN есть `vec0` и поиск по обычным таблицам с функциями расстояния. Документация
`vec0` описывает полный проход с фильтрами и разделение по ключам; подтверждения HNSW в этом
варианте не найдено. Не переносить на него характеристики HNSW из Lucene. [25–26]

[предположение] В Java практический путь — поставить `vec0.dll` нужной архитектуры, загрузить
её через xerial в каждое используемое соединение, передавать векторы через SQL/BLOB и объединять
выдачу FTS5/kNN по стабильному `rowid`. В официальном перечне интеграций Java не указана;
сочетание Windows + Java 25 + конкретные бинарники требует отдельной проверки. [23–25]

### В5. Инкрементальная индексация пополняемой почты

[предположение] Ниже предложенный шаблон, не утверждённая схема данных. Он сохраняет
индекс перестраиваемым из локального хранилища и учитывает перемещения из `plan.md 5.2`.

| Событие / объект | Предлагаемое действие |
|---|---|
| Идентификатор письма | Собственный `messageKey` внутри `connection`; отдельно таблица соответствий текущим адресам источника. `InternetMessageId` и хэш — признаки сопоставления, не безусловная уникальность. |
| Поисковый документ | Ключ из `connection`, `messageKey`, типа содержимого, идентификатора вложения и номера фрагмента. Внутренний Lucene docID не сохранять как внешний ключ. [6, 30] |
| Новое письмо / повтор синхронизации | Повторяемая замена по ключу; не `addDocument` при каждом повторе события. В Lucene — `updateDocument(Term, Document)`. [30] |

| Флаги / категории | Если живут только в хранилище, текст не переиндексировать. Если участвуют в индексном фильтре, обновлять и индекс, иначе фильтр будет устаревшим. |
| Изменение метаданных Lucene | Numeric/Binary DocValues можно менять специализированными методами; это не меняет postings или сохранённые поля. Для иной схемы заменить документ. [30] |
| Удаление письма | Удалить все его поисковые документы по общему ключу, включая вложения/векторы; удалить только папочную привязку, если остаётся другая действительная привязка. |
| Видимость удаления | Обновить читатель с применением удалений; занятое место освобождается позже при слияниях. До обновления старый снимок может видеть старое состояние. [29–30] |
| SQLite | Согласованно обновлять обычные таблицы, FTS5 и таблицу векторов в транзакции; external-content FTS5 сам не отслеживает исходную таблицу, нужны триггеры/явные записи. [21, 26] |

[предположение] Состояние синхронизации фиксировать после надёжного сохранения событий и
исходного содержимого. Индекс обновлять повторяемыми операциями с отметкой версии.
Не считать атомарными commit Lucene и запись в отдельное хранилище: после сбоя нужно повторить
незавершённые события либо перестроить индекс. [30]

[предположение] При изменении анализатора, словаря, нормализации `ё`, стоп-слов или схемы
полей увеличивать `indexSchemaVersion` / `analyzerVersion`. Построить новый каталог индекса,
догнать изменения, проверить полноту и переключить активное поколение. Старое закрывать после
освобождения читателей. Пересборка из локального текста не требует нового входа в почту. [9, 29–30]

[предположение] Отдельно версионировать модель и размерность векторов. Смена модели требует
пересчёта эмбеддингов, но не обязательно повторного извлечения текста или смены BM25-индекса.

## Рекомендация

[предположение] Основной кандидат — **Lucene 10.5.2**, начальная русская морфология —
**RussianAnalyzer / Snowball**. Для английского — параллельное поле `EnglishAnalyzer`, для
адресов, идентификаторов и полного имени файла — поля без языкового стемминга. Основания —
В1–В3; преимущество выбора — минимум собственных связующих компонентов в Java-сервере.

[предположение] Главный риск движка — самостоятельное сопровождение схемы, восстановления
согласованности и обновления индекса. Главный риск морфологии — пропуски нерегулярных форм
и отсутствие доказанного качества на почтовых запросах. Наличие стеммера закрывает техническую
возможность, но не подтверждает выполнение требования «хорошая морфология» на практике.

[предположение] Если контрольные запросы покажут существенные пропуски, сначала сравнить
Hunspell с закреплённым словарём; LuceneMorphology рассматривать после проверки адаптера 10.x
и происхождения данных. Не переходить на старый Lucene только ради неподтверждённой лемматизации.
SQLite выбрать вместо Lucene, если единая транзакционная БД важнее сложности языкового анализа
и поставки расширений; эта альтернатива требует отдельной проверки Java/Windows.

## Что не удалось проверить

- Реальные размер, память, скорость и качество: измерения запрещены брифом. На этапе реализации
  разработчику нужен обезличенный корпус с русскими/английскими запросами и длинными вложениями.
- Точные леммы LuceneMorphology для `договор` и `письмо/писем`: готовые первичные примеры не
  получены. Сверить данные конкретного коммита; не считать это проверенным преимуществом словаря.
- Текущее состояние russianmorphology: README, POM и доступная история расходятся. Перед
  зависимостью получить согласованный коммит и проверить его совместимость с Lucene 10.5.2.
- Полный вывод Hunspell, дополнительные разборы и поведение неизвестных слов: прочитаны словарь
  и правила, но фильтр не выполнялся. Проверить вместе с русским словарём выбранной версии.
- Доставка sqlite-vec в xerial на Windows/Java 25: отсутствует проверенный здесь официальный
  Java-пример. Разработчику проверить загрузку DLL, операции и восстановление; вход в почту не нужен.
- `?` H2/Tantivy: возможности настройки оболочек и готовые Windows-библиотеки не подтверждены.
  Уточнять только при возврате к этим кандидатам; API ядра не считать API оболочки.
- Полная транзитивная лицензионная ведомость, происхождение данных АОТ и актуальность ru_RU:
  закрепить артефакты/коммиты и проверить вложенные лицензии до поставки. Нового кода пока нет.

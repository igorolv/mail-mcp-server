### 1.1. Личные ящики: Gmail и Mail.ru

Источник: [RT-04](research/RT-04-imap-gmail-mailru.md). Настройки конкретных аккаунтов и
список расширений сервера (`CAPABILITY`) без входа не проверены.

| Вариант | Что это | Плюсы | Минусы / риски | Статус |
|---|---|---|---|---|
| **Gmail по IMAP** (`imap.gmail.com:993`) | Стандартный IMAP | Та же реализация, что для Mail.ru; `X-GM-MSGID`, `X-GM-THRID`, `X-GM-LABELS`; для личного Gmail IMAP всегда включён с января 2025 года | Вход — пароль приложения (нужна двухэтапная проверка, доступен не каждому аккаунту) или OAuth2 (`XOAUTH2`, область `https://mail.google.com/`); в тестовом режиме OAuth токен обновления живёт 7 дней; метки вместо папок → одно письмо в нескольких папках; ориентир лимита — 2500 МБ скачивания в сутки и до 15 клиентов | ✅ |
| Gmail API (REST) | Собственный API Google | История изменений (`history`), цепочки, метки | Нужен свой OAuth-клиент в Google Cloud и отдельная реализация источника | ✅ не сейчас |
| **Mail.ru по IMAP** (`imap.mail.ru:993`, TLS) | Стандартный IMAP | Та же реализация, что для Gmail | Нужен пароль внешнего приложения и привязанный телефон; по старым наблюдениям нет `IDLE`, есть `MOVE` и `UIDPLUS`; `CONDSTORE`/`QRESYNC` не подтверждены → синхронизация должна работать без них; OAuth для собственного клиента не проверен | 🔍 расширения проверить после первого входа |

### 1.2. EWS: операции для режима только чтения

Источник: [RT-03](research/RT-03-ews-operations.md). Всё — для `Exchange2013_SP1`.

- **Нужны 10 операций**, все только читают: `GetFolder`, `FindFolder`, `SyncFolderHierarchy`,
  `FindItem`, `SyncFolderItems`, `GetItem`, `GetAttachment`, `FindConversation`,
  `GetConversationItems`, `ConvertId`. Всё остальное — вне разрешённого списка. В RT-03 есть
  перечень операций записи, которые вызывать нельзя.
- **Синхронизация**: `SyncFolderItems` по каждой папке, до 512 изменений за вызов, повторять до
  `IncludesLastItemInRange=true`; дерево папок — `SyncFolderHierarchy`; счётчики писем
  освежать через `GetFolder` (синхронизация дерева их не сообщает). Срок жизни `SyncState` в
  документации не указан; при ошибке — полная пересинхронизация.
- **Содержимое**: `GetItem` с `IncludeMimeContent` даёт `.eml` и **не** помечает письмо
  прочитанным. MIME Exchange собирает заново — это не побайтовая копия исходного письма.
  Microsoft советует брать письма пакетами по 10.
- **Вложения**: `GetAttachment`; MIME вложенного письма — с `IncludeMimeContent`; частичного
  скачивания нет, вложение приходит целиком.
- **Идентификаторы**: `ItemId` меняется при перемещении; `InternetMessageId` не гарантирует
  уникальность экземпляра. Предложение — раздел 8, П2.
- **Нагрузка**: одновременных запросов по таблице Microsoft для 2013 — 27 (справка cmdlet
  пишет 10 — источники расходятся); выдача `FindItem` — до 1000 без фильтра, до 250 с
  фильтром или AQS. Действующую политику знает только администратор. Начинать с одного запроса
  за раз на соединение, на `ErrorServerBusy` ждать `BackOffMilliseconds`.
- **Серверный поиск**: AQS (`QueryString`) ищет и по содержимому вложений (`attachment:`), но
  только для поддержанных форматов и после индексации Exchange. Основной поиск — локальный.

### 3.1. MCP-ресурсы и поддержка клиентами

Источник: [RT-10](research/RT-10-mcp-resources.md).

- **Спецификация.** По RT-10 действующая редакция MCP — 2026-07-28; в ней подписки на ресурсы
  заменены на `subscriptions/listen`. Ресурсы, шаблоны и встроенные ресурсы есть с 2024-11-05,
  блок `resource_link` в результате инструмента — с 2025-06-18. Редакцию 2026-07-28 сами не
  проверяли.
- **Клиенты.** Claude Code и VS Code дают выбрать ресурс в контекст; Codex умеет перечислять,
  читать и получать шаблоны; у Cursor и ChatGPT поддержка описана неполно.
- **Spring AI 2.x** поддерживает `@McpResource`, `@McpComplete`, программную регистрацию и
  возврат `ResourceLink` в `CallToolResult`.
- **Вывод.** Основной доступ — инструменты поиска и чтения частями (`truncated`, `nextOffset`);
  ресурсы и `resource_link` — дополнение, через тот же фильтр секретов. `localPath` выдавать
  модели только на отфильтрованный текст: путь к исходному MIME или вложению обходит фильтр.
  Подписки отложить.

## 4. Поиск и локальная база

Источники: [RT-06](research/RT-06-search-engine.md) (движок, морфология),
[RT-07](research/RT-07-embeddings.md) (эмбеддинги).

| Решение | Что выяснили | Статус |
|---|---|---|
| **Apache Lucene** 10.5.2 (2026-10-04, Java 21+) | BM25 по умолчанию, векторы (HNSW / kNN), подсветка фрагментов, готовое объединение рангов `TopDocs.rrf` — всё внутри JVM. Риск — самим сопровождать схему индекса и его обновление | ✅ предложен (П9) |
| SQLite FTS5 + `sqlite-vec` | BM25 есть, русского стеммера нет; токенизатор — только на C, готового способа подключить его из Java не нашли; нативное расширение придётся поставлять. Так сделаны `ews-mcp`, `email-mcp`, `protonmail-local-ai` (RT-01) | ✅ альтернатива |
| `RussianAnalyzer` (Snowball) | Готов в Lucene; риск — неправильные формы: `письмо → письм`, `писем → пис` | ✅ начальный вариант |
| Hunspell + словарь LibreOffice | Запасной вариант морфологии; словарь орфографии не объединяет все формы (`писем` отдельно от `письмо`) | ✅ запасной |
| `russianmorphology` (LuceneMorphology, словарь АОТ) | Лемматизация с несколькими разборами; совместимость с Lucene 10 не подтверждена | ✅ после проверки |
| notmuch, mu (Xapian) | Готовые локальные индексаторы почты: идеи по схеме индекса, тегам, тредам | ⬜ |
| Эмбеддинги `multilingual-e5-base` / `-small` | Проверены на ruMTEB (Retrieval 67,1 / 65,8; у BGE-M3 — 74,8), есть ONNX. Оценка для 100 000 фрагментов на CPU: small — 3–13 ч, base — 10–41 ч, BGE-M3 — 41–164 ч (пересчёт, не замер) | ✅ предложены как необязательные (П12) |
| ONNX Runtime Java + DJL HuggingFace Tokenizers | Запуск модели внутри JVM; Spring AI 2.0.2 усредняет векторы, но не нормализует их — нужна своя обёртка | ✅ предложен |
| Ollama | BGE-M3, Qwen3-Embedding, EmbeddingGemma по HTTP; размер модели указывать явно (`qwen3-embedding:latest` — это 8B) | ✅ альтернатива |
| Внешние API (OpenAI, Voyage, Google и др.) | Разные правила хранения данных; только после фильтра секретов и явного включения | ✅ не по умолчанию |

| Выбор соединения | Нет соединения по умолчанию; `connection` — первый аргумент каждого инструмента | Берём для чтения; для поиска, возможно, «все ящики» (plan.md 5.7) | ✅ |
| `listConnections` | Только конфигурация, `configError`, без подключения | Берём; ошибки конфигурации не путать с ошибками входа | ✅ |
| Изоляция | Ленивое создание, блокировка на соединение, ошибка не кэшируется | Реестр берём с заменой типов; фабрика контекстов привязана к JDBC — писать свою | ✅ |
| Секреты | В файле, `${VAR}` в любой строке, незаданная переменная — ошибка старта; права через `icacls` | `EnvironmentPlaceholders` — как есть; плюс хранение OAuth-токенов Gmail | ✅ |
| Неизвестные ключи | Молча игнорируются | Лучше предупреждать в логе — опечатка в `folders` незаметна | ✅ |
| Логи | MDC с именем соединения | Берём вместе с тестом последовательных ответов stdio | ✅ |

## 8. Выводы

### 8.1. Первая очередь (RT-01…RT-05)

- **EWS-источник реален и ограничен десятью операциями чтения.** Синхронизация, MIME и вложения
  покрываются штатными операциями Exchange 2013 (раздел 1.2).
- **Готового Java-клиента EWS нет.** Официальный SDK заброшен, форки не проверены на Java 25.
  Свой тонкий SOAP-клиент на StAX реалистичен; главный технический риск — NTLM в Java
  (раздел 2).
- **Успешный вход из .NET не гарантирует вход из Java.** Нужна отдельная проверка выбранного
  HTTP-клиента: пустой домен, NTLMv2, привязка к TLS.
- **Gmail и Mail.ru — одна реализация на Angus Mail.** Синхронизация должна работать без
  расширений IMAP и ускоряться, если они есть (раздел 1.1).
- **Чужие серверы дают готовые приёмы, но не фильтр секретов.** Сначала короткие карточки поиска,
  потом подробное чтение; раздельные лимиты на ответ, диск и разбор; показывать покрытие индекса
  (раздел 3).
- **Код соседних проектов копируем с адаптацией.** Ограничения извлечения нужно усилить до общего
  лимита глубины и объёма (разделы 6–7).

### 8.2. Вторая очередь (RT-06…RT-10)

- **Поиск строим на Lucene.** BM25, векторы и объединение рангов есть в одном встраиваемом
  движке; SQLite FTS5 проигрывает из-за русского языка (раздел 4).
- **Морфология — главный риск качества поиска.** Стеммер технически решает задачу, но на
  неправильных формах ошибается; качество проверять своим набором запросов к письмам.
- **Разбор MIME — Mime4j в потоковом режиме**, плюс POI для `.msg`/TNEF, jsoup для HTML и
  iCal4j для приглашений (раздел 2).
- **Конвейер извлечения из redmine-mcp-server надо переделать до добавления почтовых парсеров.**
  RT-09 независимо подтвердил RT-05: сейчас на одном файле срабатывают все подходящие парсеры,
  `PlainTextParser` перехватывает HTML и ICS, а лимит объёма действует только внутри одного
  архива. Нужен общий счётчик глубины и объёма на всю цепочку письмо → `.msg` → ZIP → документ.
- **Фильтр секретов пишем сами.** Чужие наборы правил подходят только для машинных секретов;
  русские документы и «пароль: …» в тексте письма — свои детекторы (раздел 5).
- **Эмбеддинги можно добавить позже без смены движка:** E5 через ONNX Runtime внутри JVM, но
  первичная обработка всей почты займёт часы (раздел 4).
- **MCP-ресурсы — дополнение, не основа.** Работать нужно через инструменты; путь к исходному
  файлу модели не отдавать (раздел 3.1).

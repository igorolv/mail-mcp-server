# mail-mcp-server — план

Рабочий документ проекта: что делаем, как устроено, что проверено на реальной почте, какие
доработки возможны и какие решения приняты. Устройство кода подробно описано в инженерных
документах `docs/*-agent.md` (список — в [AGENTS.md](../AGENTS.md)). История обсуждения до
2026-10-26 — в истории git.

**Статус (2026-10-27): черновой вариант готов.** Работают оба ящика пользователя — рабочий
Exchange (EWS) и Mail.ru (IMAP). Готово:

- полная и инкрементальная синхронизация;
- письма и вложения на диске, тело и вложения в Markdown;
- поиск с русской и английской морфологией, в том числе по тексту вложений;
- фильтры дат в поиске и списках писем, поиск только по периоду;
- локальные цепочки писем между папками одного соединения;
- распознавание однозначных перемещений между папками без повторного скачивания MIME;
- снимки признаков «прочитано» и пользовательского флажка/звезды без записи в ящик;
- раскрытие вложенных писем и архивов (EML, ZIP, MSG, TNEF), текст DOC/XLS/PPT;
- необязательный фильтр секретов в ответах;
- девять инструментов MCP.

Что сделано, но ещё не проверено на реальной почте, — в разделе 2.4. Дальше — полировка и
доработки из раздела 4 по выбору пользователя.

## 1. Идея

Локальный stdio MCP-сервер, через который AI-агент (Claude Code, opencode, Codex и т. п.) читает
несколько почтовых ящиков: рабочий Exchange по EWS, Mail.ru и Gmail по IMAP. Сервер:

- скачивает письма как есть (`.eml`);
- сохраняет вложения файлами и переводит тело и вложения в Markdown;
- строит локальный индекс Lucene;
- отвечает агенту только по локальным данным.

В ящик сервер ничего не пишет. Он сделан по образцу соседних проектов: `C:\git\redmine-mcp-server`
(вложения, ограниченные ответы) и `C:\git\jdbc-mcp-server` (список соединений).

Зачем своё:

- веб-интерфейс OWA неудобен;
- готовые почтовые MCP-серверы не дают поиска по вложениям, локального индекса с русской
  морфологией и работы с Exchange 2013 по NTLM.

- **Скорость:** `listMessages` — 3–24 мс на страницу, `getMessage` — 29–49 мс, `search` с тремя

- **Формы слов:** запрос в форме множественного и единственного числа даёт одинаковое число

- **Чего не хватило:** выборки по дате — для «писем за два дня» агент листал `listMessages` по

секретов до индекса. Индекс по действующему решению хранит исходный текст, а фильтр ответов
не меняет совпадения поиска. Порог в тесте: полнота ≥ 0,91, ложных ≤ 7.

## 3. Как устроено

Подробности — в `docs/architecture-agent.md` и остальных `docs/*-agent.md`. Здесь — решения в
одном месте.

### 3.1. Принципы

1. **Диск — полная копия.** У каждого письма свой каталог:
   - `message.eml` — как его отдал сервер;
   - `meta.json` — то, чего в `.eml` нет: папка, ссылка на сервере, состояние;
   - `body.md` — тело;
   - вложения файлами, рядом с каждым его текст `<файл>.md`.
2. **Lucene — производный индекс.** Один индекс на соединение служит и каталогом, и поиском. Он
   пересобирается с диска без сети (`mail-reindex`). Версия схемы хранится в данных коммита;
   индекс старой схемы пересоздаётся при открытии.
3. **Курсоры синхронизации — в `folders.json`:** в IMAP — `UIDVALIDITY` и список UID, в EWS —
   `SyncState` из `SyncFolderItems`.
4. **Всё хранится как есть, без фильтрации.** `MAIL_MCP_REDACT_SECRETS=true` включает замену
   секретов только в текстовых полях ответов tools; по умолчанию выключено. Это защита от
   случайного попадания в контекст, а не от намеренного извлечения. Пути к оригиналам и имена
   файлов для обращения к вложениям сохраняются.
5. **Только чтение на уровне протокола:**
   - EWS: разрешённый список из 10 операций чтения;
   - IMAP: `EXAMINE`, `BODY.PEEK`, `CLOSE`, а `SELECT` и любые изменения запрещены защитой команд.
6. **Один вход за запуск, без повторов.** После отклонённого входа синхронизация этого соединения
   останавливается: устаревший пароль быстро блокирует доменную учётную запись.
7. **Pandoc обязателен** для синхронизации и переобработки. Инструменты чтения работают без него.
8. **Проще — лучше.** Пороги: письмо до 64 MiB; вложение для перевода в текст — до 20 MiB,
   XLSX — до 5 MiB включительно; ответ инструмента — страницами. Место на диске не экономим.

### 3.2. Поток данных

```
MailSource (EWS | IMAP): folders() · changes() · metadata() · download()
        │
        ▼
SyncRunner — один запуск на соединение, только в процессе, взявшем IndexWriter
  1. восстановление: каталоги без meta.json удалить, документы без каталога удалить,
     каталоги без документа доделать по состоянию; при расхождении папки/ссылки/флагов с meta.json
     восстановить только затронутые документы из сохранённого содержимого
  2. папки: сопоставить по remoteId; новые — ключ f<n>; собрать изменения и метаданные
     всех включённых папок до удалений; сохранить папки со старыми/null курсорами,
     включая пропавшие папки до завершения их удалений
  3. однозначные перемещения: атомарно изменить meta.json → загрузить сохранённое
     содержимое в индекс → commit; затем остальные удаления и скачивание пачками по 100
       message.eml + meta.json (downloaded) → разбор MIME → вложения, body.md, <файл>.md
       → meta.json (converted | failed) → документ индекса; commit после пачки
  4. после всех изменений и коммитов — все новые курсоры и итоговый список папок
     одним сохранением folders.json; ход — в sync-status.json
        │
        ▼
Инструменты MCP: folders.json, sync-status.json, индекс и каталоги писем; в сеть не ходят
```

### 3.4. На диске

```
%USERPROFILE%\.mail-mcp-server\
  connections.json, logs/
  <connection>/
    folders.json, sync-status.json
    messages/<k2>/<key>/          — key — UUID, k2 — его первые два символа
      message.eml, meta.json, body.md
      attachments/1__отчёт.pdf, 1__отчёт.pdf.md
    index/                        — Lucene, схема 4
```

Имя вложения — `<номер>__<имя из письма>`:

- запрещённые в Windows символы и управляющие символы заменены на `_`;
- имя обрезано до 100 символов;
- если имени нет — `<номер>__part`.

Извлечённые из контейнеров файлы продолжают общую нумерацию в том же каталоге; поле `parent`
ссылается на имя файла непосредственного контейнера. Список восстанавливается из файлов без
новых полей метаданных для контейнеров; используется текущая схема индекса 4.

JSON-файлы пишутся во временный файл и переименовываются.

Необязательный `MessageMeta.fingerprint` хранит серверные `messageId`, `size`, `sentAt`,
`from`, `subject`; старый JSON читается с `null`. Размер в отпечатке — размер из источника,
а `MessageMeta.size` — размер скачанной MIME: в EWS они могут различаться. Переобработка и
переиндексация сохраняют отпечаток; в индекс он не добавляется.
Необязательные Boolean `read` и `flagged` хранят последние успешно наблюдённые значения:
старый JSON даёт `null`, неизвестное значение не записывается, `false` сохраняется явно.
Переобработка, ошибки MIME и переиндексация сохраняют флаги. В схеме 4 известные значения
индексируются хранимыми строковыми полями `true`/`false`; неизвестные поля отсутствуют.
Старый индекс автоматически пересобирается с диска при открытии писателя; `mail-reindex`
делает это без сети. Без синхронизации неизвестные удалённые флаги получить нельзя.
При распознанном перемещении меняются папка, серверная ссылка, отпечаток и наблюдённые
флаги назначения; UUID,
каталог, состояние, ошибка, MIME, SHA-256, время скачивания, тело и файлы вложений сохраняются.

### 3.5. Разбор, Markdown и поиск

- **MIME:** Angus Mail. Нужны три системных свойства, их выставляет `main`:
  - `mail.mime.decodefilename` — имена в encoded-word;
  - `mail.mime.parameters.strict=false`;
  - `mail.mime.base64.ignoreerrors`.
- **Тело письма:** первая часть `text/plain`, иначе первая `text/html` через pandoc. Кодировка —
  заявленная в письме, без угадывания.
- **Вложения:** все прочие листовые части. После MIME-разбора раскрываются вложенные `.eml`,
  ZIP, MSG (POI HSMF) и TNEF (POI HMEF): файлы добавляются в плоский список с полем `parent`,
  с общей нумерацией в `attachments/`.
  Список восстанавливается из сохранённых контейнеров; чтение не пишет файлы. Глубина — до 5,
  запись ZIP — до 20 MiB, на письмо — до 1000 извлечённых файлов и 256 MiB для всех контейнеров
  вместе. Встроенные MAPI-сообщения сохраняются как самостоятельные `.msg` с адаптированным
  заголовком свойств и таблицей именованных свойств. Исходные MIME и контейнеры не меняются;
  внешние ссылки не открываются. POI заранее загружает данные в память: ограничения относятся
  к извлечённому результату, а не гарантируют предел памяти парсера. S/MIME остаётся непрозрачным.
  Для существующих писем нужен `mail-reprocess`, одного `mail-reindex` недостаточно. Новые
  контейнеры могут изменить номера последующих извлечённых файлов; перед обращением к вложениям
  и поиском нужно закончить переобработку соединения. Один проход обновляет и контейнеры,
  и текст старых форматов Office.
- **Текст вложений** (до 20 MiB декодированных байтов, XLSX — до 5 MiB включительно):
  - pandoc для DOCX, ODT, RTF, EPUB, HTML и CSV;
  - PDFBox для PDF;
  - POI для DOC/XLS/PPT (Office 97–2003), XLSX и PPTX; формулы не вычисляются, макросы и внешние
    ссылки не выполняются; пустые, повреждённые и зашифрованные документы остаются без текста;
  - обычный текст — как есть;
  - вложенные `.eml` — заголовки и выбранное тело; HTML через pandoc;
  - MSG — доступные заголовки и первое непустое тело: plain, иначе HTML, иначе RTF; HTML/RTF
    через pandoc. Объявленные кодировки применяются без угадывания: при наличии обеих
    `MESSAGE_CODEPAGE` используется для заголовков и plain, `INTERNET_CPID` — для HTML;
  - TNEF — доступная тема и RTF-тело через pandoc; тело не становится отдельным вложением.

  Порог XLSX проверяется по фактическому размеру файла после определения формата, до вызова
  `XlsxText.extract`; размер из метаданных не используется. Это распространяется на вложения
  внутри контейнеров; бинарный XLS и остальные форматы сохраняют порог 20 MiB. Превышение
  оставляет оригинал без нового `.md`, не меняет состояние письма и не добавляет ошибку.
  Сжатый размер XLSX не ограничивает память eager-разбора POI: меньшие файлы тоже могут быть
  дорогими. Порог снижает риск, но не гарантирует отсутствие нехватки памяти; подтверждённого
  падения JVM нет. Ошибка перевода оставляет вложение без `.md`, письмо остаётся `converted`.
  Сохранённый ранее текст доступен чтению и поиску до необязательной пользовательской
  `mail-reprocess`: она удаляет старый `.md` и индексированный текст XLSX свыше 5 MiB,
  сохраняя исходную MIME и байты вложения. Чтение и `mail-reindex` для `converted` используют
  сохранённый текст без применения нового порога. Используется схема индекса 4; пороги скачивания
  и раскрытия контейнеров не меняются.
- **Pandoc:** отдельный процесс `pandoc --sandbox` на каждое преобразование, около 27 мс.
  `pandoc server` не подошёл: он слушает все сетевые интерфейсы.
- **Поиск:** Lucene 10.5.2, `SimpleQueryParser` — все слова обязательны, кавычки дают фразу.
  - Поля: русское (`RussianAnalyzer`), английское (`EnglishAnalyzer` с английскими и русскими
    стоп-словами), точные адреса и имена файлов, части имён файлов.
  - Сниппет — один фрагмент через `UnifiedHighlighter`: для `any` совпадение в теле имеет
    приоритет, иначе берётся первое подходящее вложение в расширенном списке; для `attachmentText`
    выбирается вложение. Остальные группы полей сохраняют сниппет из тела.
  - Текст вложения читается из сохранённого `.md` только для результатов текущей страницы.
    `snippetAttachmentFile` — точное имя для `getAttachment`, `snippetAttachmentName` —
    отображаемое имя (при отсутствии — имя файла). Для сниппета из тела эти поля отсутствуют.
    Если MIME или подходящий текст вложения недоступны, возвращается контекст тела, а без
    тела — результат без сниппета. Само найденное письмо остаётся в выдаче.
  - Источник сниппета выбирается по исходному тексту; при включённом фильтре полный выбранный
    текст очищается до подсветки. Имя файла сохраняется, отображаемое имя фильтруется.
    Совпадения, оценки и страницы не меняются. Сниппеты используют текущую схему индекса 4
    и сохранённые `.md` без переобработки.
  - Если весь запрос после удаления пробелов по краям — полный адрес, поля отображаемых имён
    `fromName`, `toName`, `ccName` исключаются. Остальные поля выбранной группы сохраняются,
    в том числе тело для `any`. Переиндексация не нужна.
- **Логи PDF:** PDFBox и FontBox пишут только ошибки (`ERROR`) в обеих конфигурациях логов;
  предупреждения о повреждённых, но читаемых PDF не засоряют отчёт команды.
- **Фильтр ответа:** пароли RU/EN, коды подтверждения, URI с паролем, Basic/Bearer,
  JWT/JWE, приватные PEM-ключи, токены GitHub и поля API-секретов заменяются типовыми
  маркерами. Персональные данные не входят в эту доработку. Полный текст очищается в памяти
  до нарезки и построения сниппета; позиции и длины относятся к очищенному представлению.
  Совпадения, оценки и количество результатов поиска не меняются. Перестроение индекса не
  требуется. Правила и ограничения — в `docs/redaction-agent.md`.

### 3.6. Синхронизация и процессы

- Запуск только по запросу: инструмент `sync` (в фоне процесса сервера) или команда `mail-sync`.
  Синхронизируется всё, дальше — инкрементально.
- Синхронизирует только держатель замка записи Lucene. Другие процессы читают; на попытку
  синхронизации они получают `lockedByOtherProcess`.
- `sync-status.json` пишет только держатель замка. Если записанный там процесс уже не жив,
  `syncStatus` показывает `interrupted`.
- Прогресс папки различает `reset` и `rescanned`: смена IMAP `UIDVALIDITY` инвалидирует
  серверные ссылки (`reset=true`, `rescanned=false`), локальные письма папки заменяются.
  Если первый запрос с непустым EWS `SyncState` получает `ErrorInvalidSyncStateData`, источник
  один раз начинает обход без состояния. Успешный обход даёт `reset=false`, `rescanned=true`:
  известные письма не скачиваются повторно, отсутствующие на сервере удаляются локально.
  Обычный первый обход не считается повторным. Ошибка после перезапуска или на последующих
  страницах передаётся вызывающему коду без нового повтора. Признак сохраняется в каждом
  отчёте затронутой папки; в старом JSON без `rescanned` он читается как `false`.
- Каждый начавшийся фоновый запуск после закрытия источника и индекса пишет одну строку INFO:
  `Background sync finished: state={}, durationMs={}, downloaded={}, failed={}, removed={}`.
  Длительность измеряется монотонными часами; `completed` означает успех запуска и закрытия,
  иначе итог — `failed`. Счётчики суммируют последние накопительные отчёты папок:
  `downloaded` — новые письма, доведённые до `converted`, `failed` — ошибки отдельных писем,
  `removed` — локально удалённые письма. Ошибка всего запуска не прибавляет ошибочное письмо;
  неотчитанная часть незавершённой пачки может не попасть в итог. При ошибке закрытия ресурсов
  сохранённый статус может остаться `completed`, а итог в логе — `failed`.
  Строка не содержит имён соединений, папок или данных писем; отказанные и не начавшиеся
  запуски её не пишут. Вывод CLI, запись статуса и владение замком не меняются.
- После отклонённого входа в статусе ставится `signInRejected`. Тогда `sync` отказывает во всех
  процессах, пока пользователь не исправит соединение и не выполнит `mail-sync` из терминала.
- Папки:
  - IMAP: все, кроме `\Noselect`, `\Trash`, `\Junk`, `\Drafts`;
  - EWS: класс `IPF.Note*` под корнем ящика, кроме удалённых, нежелательной почты, черновиков,
    исходящих и их подпапок.
- При каждом запуске для всех присутствующих ссылок, включая известные письма, читается
  один снимок метаданных на папку, запросами до 100 ссылок: EWS `GetItem` с `IdOnly` и пятью
  свойствами идентичности, `message:IsRead` и `item:Flag`, IMAP `ENVELOPE`, UID, `RFC822.SIZE`
  и `FLAGS`, без MIME и тела. IMAP повторяет
  `EXAMINE` и сверяет `UIDVALIDITY` с результатом обнаружения изменений; расхождение прерывает
  запуск без повтора. Первый обычный запуск заполняет отпечатки старых писем без повторного
  скачивания и переобработки. Неполный свежий отпечаток очищает сохранённый до `null`.
- Перемещение распознаётся эвристически: старое `converted`-письмо с MIME явно удаляется
  этим запуском, новая ссылка находится в другой включённой папке того же соединения,
  полный отпечаток совпадает и встречается ровно один раз среди старых и текущих серверных
  писем. Нужны единственный непустой `Message-ID` в угловых скобках без пробелов внутри,
  положительный серверный размер, дата отправки, непустые адрес отправителя и тема.
  У ID и адреса обрезаются только внешние пробелы; регистр и декодированная тема сравниваются
  точно. Старые кандидаты фиксируются до обновления метаданных оставшихся писем.
  Оставшаяся идентичная копия, неоднозначность, отсутствие сохранённого отпечатка или MIME,
  состояния `downloaded`/`failed` и сброс `UIDVALIDITY` любой из двух папок исключают
  повторное использование. Обычный повторный обход EWS сбросом не считается.
  В остальных случаях перемещение остаётся удалением и скачиванием с новым ключом.
- Риск эвристики принят пользователем: одинаковые метаданные могут скрывать разные байты.
  SHA-256 относится только к сохранённому оригиналу; удалённая побайтовая идентичность
  не проверяется. Распознанное перемещение не увеличивает `downloaded`, `failed` или `removed`;
  ноль скачиваний может включать повторно использованные письма.
- Изменения всех папок обнаруживаются до удалений. Сначала применяются перемещения, затем
  остальные удаления с проверкой прежней папки/ссылки в метаданных. Пропавшая папка не удаляет
  уже переназначенный каталог. Все курсоры обновляются только после завершения изменений
  и коммитов индекса; до этого сохраняются старые/null курсоры и записи пропавших папок.
  После прерывания сверка индекса с `meta.json` восстанавливает изменённые ссылки и флаги из файлов,
  а текущие локальные ссылки позволяют пропустить уже сохранённые добавления. Проверены
  прерывания после переназначения метаданных, после коммита и перед сохранением курсоров:
  ключ и содержимое сохраняются без повторного скачивания. Журнала и второго хранилища нет.
- Каждый снимок обновляет `read` и `flagged` независимо: отсутствующее/неподдерживаемое
  значение сохраняет известное, явное `false` снимает признак. EWS `Flagged` даёт `true`,
  `NotFlagged`/`Complete` — `false`; пустой IMAP `FLAGS ()` даёт оба `false`.
  `flagged` означает пользовательский флажок/звезду, не Importance отправителя или Gmail
  Important. Это конкретный контракт реализации, а не новое решение пользователя.
  IMAP использует фактический ответ пачки, не кэшированные геттеры флагов; отсутствие FLAGS
  оставляет неизвестное значение, ошибка разбора прерывает запуск без повтора.
- Изменившиеся флаги атомарно сохраняются в метаданных и обновляют документ индекса из
  сохранённого содержимого, без скачивания или конвертации. Неизменившиеся флаги не вызывают
  перезаписи метаданных/документа. Время скачивания, состояние, ошибка и файлы не меняются;
  счётчики скачанных/ошибочных/удалённых писем не растут. Новые письма получают наблюдённые
  флаги даже при неудаче скачивания. Флаги не входят в отпечаток перемещения; при повторном
  использовании применяются наблюдения назначения, при сбросе UIDVALIDITY — только свежие.
- Отдельно разбирать EWS Update/ReadFlagChange не требуется: полный проход метаданных
  наблюдает итоговые флаги даже без добавлений/удалений. Цена — запросы метаданных всех
  присутствующих писем при каждом запрошенном запуске. Метки не синхронизируются.

### 3.7. Инструменты и команды

| Инструмент MCP | Что делает |
|---|---|
| `listConnections` | соединения из конфигурации, без обращения к серверам |
| `sync`, `syncStatus` | фоновая синхронизация; ход и итог последнего запуска, отдельные признаки `reset` и `rescanned` по папкам |
| `listFolders` | папки с числом писем и признаком «пройдена целиком» |
| `listMessages` | карточки писем папки от новых к старым, страницами; необязательные границы даты `since`/`until` |
| `getMessage` | заголовки, тело кусками, вложения с путями к файлу и к `.md` |
| `getThread` | карточки цепочки между папками одного соединения по локальному UUID письма, от старых к новым, страницами |
| `getAttachment` | текст вложения кусками, путь к файлу |
| `search` | поиск по полям (`any`, `subject`, `body`, `from`, `to`, `attachmentName`, `attachmentText`) и/или датам: карточки, оценка, сниппет для текстового запроса |

`since` включается в интервал, `until` исключается; каждая граница необязательна, вместе
они требуют `since < until`. Используется дата заголовка MIME из существующего `date`
(`LongPoint`), а не время получения или скачивания. Допустимы строгая дата `YYYY-MM-DD`
(полночь UTC) и ISO-8601 с явным `Z` или числовым смещением, с точностью не мельче миллисекунды
и в диапазоне epoch milliseconds. В ответе границы нормализуются в UTC. Для 2026-10-26–27
нужны `since=2026-10-26`, `until=2026-10-28`. Письма без даты попадают только в запросы без
границ. Фильтры используют существующее поле даты в текущей схеме индекса 4.

У `search` можно опустить `query` или передать пустой текст только при наличии границы даты.
Поиск без слов охватывает все локальные папки соединения, если не задана папка, сортирует
от новых к старым, затем по ключу, возвращает `score=0` без `query`, сниппета и атрибуции
вложения и не читает MIME или соседние текстовые файлы. `listMessages` по-прежнему требует
папку. Текстовый поиск сохраняет BM25, подсветку и атрибуцию вложений; фильтры не входят в
запрос подсветки. Поле и папка проверяются в обоих режимах; запрос только из стоп-слов
остаётся текстовым с нулём результатов. Оба инструмента проверяют актуальность схемы;
подсчёт и страница используют один запрос и один снимок индекса.

`getThread(connection, key, offset, limit)` строит неориентированный граф только по сохранённым
`Message-ID`, `In-Reply-To` и `References` живых документов одного снимка индекса. Локальные
ключи и ID заголовков — отдельные узлы; ключ связан со своим ID и всеми ID ответа и ссылок.
Сравнение учитывает регистр. ID должен быть непустым, в угловых скобках, без пробелов и
вложенных скобок; `Message-ID` после обрезки пробелов должен состоять ровно из одного ID,
из заголовков ответа извлекаются все корректные ID без повторов. Граф связывает предков,
потомков и ответы на отсутствующего родителя; циклы завершаются. Копии с разными ключами
остаются отдельными карточками; тема, участники, даты и ID провайдера связей не создают.

Сначала находится вся компонента, затем она сортируется по возрастанию даты, без даты —
в конце, при равенстве — по ключу. `total` точен для снимка; `offset` по умолчанию 0,
`limit` — 50, максимум 200. За концом возвращается пустой список без `nextOffset`.
Некорректные аргументы отклоняются до открытия индекса; отсутствие индекса или ключа
даёт ошибку `Message is not indexed; use listMessages`, старая схема — ту же ошибку
пересборки, что и поиск. Письмо без пригодных заголовков, в том числе `failed`, даёт
одну карточку.

Сканируются только ключи и заголовки, даты берутся из doc values, поля карточек — только
для страницы. Ответ содержит ключ, ключ папки, дату, отправителя, тему, признак вложений,
состояние и абсолютный путь каталога; тела и исходных ID заголовков нет. Фильтр секретов
применяется только к теме и отображаемому отправителю. Чтение работает при занятом замке
писателя, без MIME, текста тела и вложений, источника и pandoc. Используется схема 4;
сохранённых цепочек и кэша нет. Между вызовами страницы могут
измениться при синхронизации, как у `listMessages`.

`getMessage`, `listMessages`, текстовый поиск и поиск только по датам, `getThread` возвращают
необязательные Boolean `read`/`flagged`; неизвестные поля отсутствуют. Это последний
успешно наблюдённый снимок, не текущее состояние ящика. `getMessage` берёт флаги из
метаданных даже при ошибке разбора MIME; остальные — из зафиксированного индекса.
Флаги не проходят через фильтр секретов. Новых фильтров, счётчиков и инструментов записи нет.

Команды jar, их запускает пользователь:

- `mail-sync`;
- `mail-reprocess` и `mail-reindex` (обе без сети);
- `gmail-oauth`.

### 3.8. Чего не делаем без решения пользователя

- общих бюджетов, счётчиков и сроков разбора, отдельного процесса для разбора. Исключение —
  утверждённые лимиты раскрытия контейнеров (раздел 3.5, решение в разделе 5): константы на одно
  письмо, без настроек и общего объекта бюджета;
- SQLite или другой базы рядом с индексом;
- состояний сверх `downloaded`/`converted`/`failed` с причиной;
- своего перевода HTML в текст и угадывания кодировок;
- запасного пути на случай отсутствия pandoc;
- автоматических повторов входа и записи в ящик;
- защит «на будущее», которых не требует задача.

## 7. Как ведётся работа

- Пользователь выбирает доработки из раздела 4.
- Для каждой пишется бриф в [docs/impl-tasks/](impl-tasks/README.md). Брифы больших доработок
  (L) и проверку рискованных изменений делает сильная модель (Claude). Остальное — любая
  способная модель (ChatGPT/Codex).
- Каждый бриф проходит три отдельные сессии по готовым промтам из `docs/impl-tasks/README.md`:
  1. реализация без коммита;
  2. проверка по списку с вердиктом и, если нужно, промтом на исправление;
  3. запись в план и коммит.
- Проверки на настоящих ящиках запускает только пользователь. В документы попадают только числа,
  без имён папок, адресов и содержимого писем.
- После приёмки:
  - строка удаляется из раздела 4, номер добавляется в список сделанных над таблицей;
  - сделанное описывается в разделе 3;
  - новое проверенное — в раздел 2, а то, что ещё ждёт проверки на реальной почте, — в 2.4;
  - новое решение пользователя — в раздел 5;
  - бриф удаляется.

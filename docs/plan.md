# mail-mcp-server — план и обсуждение

Рабочий документ для обсуждения идеи. Здесь фиксируем цели, решения, открытые вопросы и ход
обсуждения. Исследование существующих решений и протоколов доступа — в [research.md](research.md).

Статус: **этап 1 — спайки EWS и IMAP Mail.ru подтверждены на реальных ящиках**
(2026-10-25, разделы 3.3–3.4). Есть каркас сервера, список соединений, клиенты EWS и IMAP.
Подключение личного Gmail отложено пользователем; в его локальной конфигурации только `work`
и `mailru`. Поддержка Gmail/OAuth2 сохранена, успешный вход в Gmail пока не подтверждён.
Синтетические наборы RT-11…RT-13 созданы.
Локальный конвейер пока не реализован. Архитектура переписана 2026-10-25 (раздел 6),
следующий шаг — 7.1.

## 1. Идея в одном абзаце

Локальный stdio MCP-сервер для нескольких почтовых ящиков — рабочего Exchange, Gmail и Mail.ru, —
сделанный «по образцу» `C:\git\redmine-mcp-server`. Ящики описываются списком соединений, как
базы в `C:\git\jdbc-mcp-server` (раздел 5.7). Сервер даёт AI-агенту (Claude Code, Cursor и т.п.) читать почту,
скачивает письма и вложения в локальную папку, извлекает из вложений текст, строит локальный
поисковый индекс по письмам **и** вложениям («RAG на минималках»: BM25 по умолчанию, эмбеддинги —
опционально) и пропускает всё, что уходит в LLM, через фильтр чувствительных данных.
По умолчанию — только чтение; отправка писем — позже и опционально.

## 2. Зачем своё, если решения уже есть

- Веб-интерфейс OWA (`https://webmail.example.com/owa`) неудобен.
- Нужны свои доработки, которых нет в готовых решениях: фильтр секретов, поиск по вложениям,
  локальный индекс, оформление писем как MCP-ресурсов.
- Есть отработанный образец (redmine-mcp-server): архитектура, пайплайн извлечения текста из
  вложений, снапшоты на диске, ограничения размера ответов.
- Готовые решения всё равно изучаем — для идей и правил (см. [research.md](research.md)).

### 3.1. Проверка эндпоинтов (2026-10-24)

Анонимные запросы `curl` без авторизации, смотрели только заголовки ответа.

| URL (оба хоста: `webmail.` и `mail.example.com`) | Ответ | `WWW-Authenticate` |
|---|---|---|
| `/EWS/Exchange.asmx` | `401 Anonymous Request Disallowed` | `Negotiate`, `NTLM`, `Basic` |
| `/autodiscover/autodiscover.xml` | `401 Anonymous Request Disallowed` | `Negotiate`, `NTLM`, `Basic` |
| `/Autodiscover/Autodiscover.svc` | `401 Anonymous Request Disallowed` | `Negotiate`, `NTLM`, `Basic` |
| `/Microsoft-Server-ActiveSync` | `401 Unauthorized` | только `Basic` |
| `/owa/` | `302` → `/owa/auth/logon.aspx` (форма входа) | — |

Общие заголовки: `Server: Microsoft-IIS/8.5`, `X-OWA-Version: 15.0.1497.x`, одинаковый
`X-FEServer` на обоих хостах.

DNS и TLS:

- `webmail.example.com` и `mail.example.com` указывают на **один IP** и отвечают одним и тем
  же фронтендом, то есть это один сервер под двумя именами.
- Сертификат — wildcard на домен компании от публичного удостоверяющего центра.
- `autodiscover.example.com` **не резолвится**, SRV-записи `_autodiscover._tcp.example.com`
  нет. Autodiscover доступен только по пути `/autodiscover/...` на основных хостах.

Выводы:

- **EWS доступен из интернета** — основной кандидат на протокол подтверждён.
- **Версия: Exchange 2013** (сборка 15.0.1497.x — это CU23, последнее накопительное обновление
  2013; IIS 8.5 — Windows Server 2012 R2). Поддержка Exchange 2013 у Microsoft закончилась
  в апреле 2023 года. Значит, новых API не будет, ориентируемся на EWS схемы Exchange 2013
  (`Exchange2013_SP1`).
- **Аутентификация для EWS**: Basic по HTTPS (самый простой вариант для Java), NTLM и Negotiate
  (Kerberos/NTLM) тоже предложены. Kerberos/SSO возможен только с доменной машины.
- Autodiscover в клиенте делать не обязательно: URL EWS можно задавать в конфигурации явно.
- Пока не проверено: работает ли Basic из кода, лимиты троттлинга EWS, включены ли IMAP/SMTP.

### 3.2. Вход с учётными данными (2026-10-24)

- **Браузер: успех.** `https://webmail.example.com/EWS/Exchange.asmx`, доменный логин и
  пароль в окне браузера. Машина не в домене, поэтому браузер, скорее всего, вошёл через
  NTLM (через Negotiate). Значит, учётная запись имеет доступ к EWS.
- **Скрипт [scripts/ews-login-check.ps1](../scripts/ews-login-check.ps1), первая версия: неуспех.**
  Пробовал только `user@example.com` и `example.com\user` (Basic и NTLM).
  Механика скрипта проверена анонимным запросом: запрос уходит, ответ `401` разбирается.
  Причина — формат логина. В скрипт добавлены логин без домена (`user`) и метод `Negotiate`.
- **Скрипт, вторая версия: успех.** `-Logins user -Methods NTLM`, одна попытка:

  | Метод | Логин | HTTP | Результат | Папка | Всего | Непрочитано |
  |---|---|---|---|---|---|---|
  | NTLM | `user` | `200 OK` | `Success` / `NoError` | Входящие | 1987 | 691 |

Выводы:

- **Рабочая схема входа из кода: NTLM, логин без домена (`user`).** Домен подставляет
  сервер. Форматы `user@example.com` и `example.com\user` в первой версии не
  прошли (точный ответ по каждому не сохранился).
- `RequestServerVersion Exchange2013_SP1` принимается, кириллица в ответе (`Входящие`)
  приходит корректно в UTF-8.
- Объём: во «Входящих» ~2000 писем — для локального индекса это немного; общий объём по всем
  папкам ещё предстоит оценить.
- **Следствие для Java.** Встроенный `java.net.http.HttpClient` NTLM не умеет. Варианты:
  Apache HttpClient 5 (NTLM есть, но помечен устаревшим), реализация NTLM в `ews-java-api`
  (на Apache HttpClient 4), либо Basic, если он работает. Basic для EWS пока не проверен.
- **Basic с логином без домена: неуспех (2026-10-24).** `-Server mail.example.com -Logins user
  -Methods Basic`, одна попытка: `401 Unauthorized`, сервер снова предлагает `Negotiate`, `NTLM`,
  `Basic`. Вероятная причина — при Basic IIS не подставляет домен к логину без домена, как это
  делает NTLM. Basic с доменом (`example.com\user`, как в настройке iPhone для ActiveSync, где
  сервер предлагает только Basic) отдельно не проверяли; опечатку в пароле одна попытка тоже не
  исключает. На решение П1 это не влияет: клиент EWS в Java — NTLM через Apache HttpClient 5.

### 3.3. Спайк EWS на Java (2026-10-25)

Пользователь запустил `java -jar build\libs\mail-mcp-server.jar ews-spike work` с реальным
EWS-соединением. По присланному диагностическому выводу все три операции успешны,
итог — `RESULT: OK`:

| Операция | Время | Результат |
|---|---|---|
| `GetFolder inbox` | 463 мс | «Входящие», `IPF.Note`, 1987 писем, 691 непрочитанное, 1 подпапка |
| `FindItem` для самого нового письма | 63 мс | Письмо найдено; `TotalItemsInView = 1987` — размер представления, а не число скачанных писем |
| `GetItem` с MIME | 439 мс | Сохранён один `.eml`, 26047 байт, рассчитан SHA-256 |

Выводы и границы проверки:

- NTLM из Java через Apache HttpClient 5 работает с настроенным сервером. После `GetFolder`
  было 3 HTTP-запроса (рукопожатие NTLM); всего — 5, то есть соединение после входа
  использовано повторно для `FindItem` и `GetItem`.
- Запасной транспорт на `HttpsURLConnection` для проверенного соединения сейчас не нужен;
  это не проверка настроек Extended Protection на других серверах.
- `IsRead` до и после получения MIME — `true`. Флаг не изменился, но отсутствие перехода
  `false → true` на непрочитанном письме этим запуском не проверено.
- Оригинал сохранён в `<каталог данных>\work\spike\`; содержимое письма агент не открывал.
  Реальные адреса, локальный пользовательский путь и хэш письма в документацию не перенесены.

## 4. Цели и не-цели

### Цели (MVP и ближайшие этапы)

0. Несколько почтовых ящиков сразу: список соединений в отдельном файле, у каждого свой тип
   (EWS, IMAP), свои свойства и учётные данные (раздел 5.7).
1. Чтение почты: папки, списки писем, письмо целиком, цепочки (threads).
2. Вложения: скачивание в локальную папку по запросу, извлечение текста (PDF, DOCX, XLSX, PPTX,
   ZIP, txt…), возврат `localPath`/`fileUri` — как `getAttachment` в redmine-mcp-server.
3. Локальное хранилище писем (снапшоты на диске) с инкрементальной синхронизацией.
4. Локальный поиск по теме, телу и тексту вложений: BM25 по умолчанию.
5. Фильтр чувствительных данных между почтой и MCP-ответом.
6. Режим «только чтение» по умолчанию.

### Позже / опционально

7. Эмбеддинги и гибридный поиск (BM25 + векторы).
8. Письма и вложения как MCP-ресурсы.
9. Запись: черновики, ответ, отправка, перемещение, флаги — отдельно включаемый режим.

### Не-цели (пока)

- Полноценный почтовый клиент / замена Outlook.
- Календарь, контакты, задачи Exchange (можно вернуться позже).
- Поддержка всех почтовых систем. Нужны два типа источника: EWS (рабочий Exchange) и IMAP
  (Gmail, Mail.ru). Graph, Gmail API, POP3 и ActiveSync — не сейчас.

## 5. Ключевые идеи (черновик для обсуждения)

### 5.1. Вложения → локальные файлы

Повторяем подход redmine-mcp-server: при обращении к вложению оригинал сохраняется в локальный
каталог, текст извлекается пайплайном парсеров (PDFBox, POI, Tika, pandoc), ответ ограничен
по размеру и «восстанавливаем» (есть путь к оригиналу и способ запросить продолжение).

Отличие от Redmine: в почте вложения бывают вложенными письмами (`.eml`, `.msg`, item
attachments в EWS) — нужен парсер для них (рекурсивно, с ограничением глубины). Также inline-
картинки в HTML-теле (`cid:`) и `winmail.dat` (TNEF).

→ *Решено 2026-10-24 (раздел 10, П10):* разбор писем — Apache James Mime4j в потоковом режиме;
новые парсеры `.eml`, `.msg` (POI HSMF), TNEF (POI HMEF), HTML-тело (jsoup), `.ics` (iCal4j),
распознавание S/MIME без расшифровки. Конвейер из redmine-mcp-server сначала переделать: один
текст на файл, общий лимит глубины и объёма на всю цепочку вложенности, разбор в отдельном
процессе с ограничением памяти и времени. Подробности — research.md, разделы 2 и 6.

→ *Пересмотрено пользователем 2026-10-25 (раздел 10):* отдельный процесс для разбора и общие
лимиты на всю цепочку вложенности отменены как ненужное усложнение. Реализация офлайн-разбора
MIME (коммит `d6534ca`) откачена: у неё не было ни вызывающего кода, ни потребителя результата.
Способ разбора MIME будет выбран заново вместе с моделью объектов (раздел 9).
→ *Выбран 2026-10-25:* Angus Mail, без отдельной библиотеки (раздел 6.7).

### 5.2. Почта — пополняемые данные → локальная база

Почта в основном **дописывается**, а не меняется: новое письмо приходит, старое почти не
редактируется. Поэтому:

- синхронизация инкрементальная (в EWS есть `SyncFolderItems` со sync state);
- письмо можно один раз скачать, распарсить, проиндексировать и больше не трогать;
- индекс — тоже в основном append-only.

Нюансы, которые «пополняемость» нарушают: перемещение между папками, удаление, флаги
прочитано/важно, категории. Нужен стабильный ключ письма: EWS `ItemId` может меняться при
перемещении, поэтому рассмотреть `InternetMessageId` (+ хэш) как основной идентификатор.

→ *Решено 2026-10-24 (раздел 10, П2):* `InternetMessageId` основным ключом **не** берём — он не
гарантирует уникальность экземпляра (research.md 1.2). Ключ письма — локальный UUID в рамках
соединения; отдельно хранятся текущий адрес на сервере (EWS `ItemId`, IMAP `UIDVALIDITY` + `UID`),
`Message-ID` и хэш MIME — для сопоставления при перемещениях. Письмо Gmail хранится один раз по
`X-GM-MSGID`, метки — отдельно.

→ *Решено 2026-10-24 (раздел 10, вопросы 7 и 8):*

- **Что синхронизируется по умолчанию:** все настоящие почтовые папки, кроме «Удалённых», «Спама»,
  «Исходящих», «Черновиков» и поисковых папок; за всю историю. В Gmail — «Вся почта» один раз с
  метками, без «Спама» и «Корзины». Иначе — полями `folders` и `since` в соединении.
- **Когда:** только по запросу — отдельным инструментом синхронизации с параметром глубины:
  «только новое» (по умолчанию), «за N дней», «ещё N писем вглубь истории», «вся история».
  Новые изменения приходят инкрементально; история догружается от новых писем к старым порциями
  и продолжается с места остановки. Инструмент запускает работу в фоне своего экземпляра и сразу
  отвечает; прогресс — через `indexStatus`. Автоматической фоновой синхронизации нет.
- **Удаления и перемещения** приходят той же инкрементальной синхронизацией и учитываются — поиск
  не должен находить удалённые письма.
- **Остальные инструменты** отвечают сразу, только по локальным данным, и показывают покрытие.
- **Вложения:** текст извлекается при синхронизации для вложений до настраиваемого размера
  (например, 20 МБ); у больших — только метаданные, текст при первом обращении; поиск показывает,
  что не проиндексировано.
- **Несколько экземпляров сервера** (разные сессии и клиенты) используют общую базу. Читают все;
  синхронизирует и пишет в индекс только экземпляр, взявший **блокировку соединения** (файловая
  блокировка ОС + запись в SQLite: кто, с какого времени, прогресс). Остальные отвечают «идёт в
  другом экземпляре» и продолжают читать; читатели Lucene переоткрывают индекс после записи.
  Блокировка ОС снимается сама, если процесс упал.
- **Ошибка входа** останавливает синхронизацию соединения без повторов до перезапуска или правки
  конфигурации — иначе устаревший пароль быстро заблокирует доменную учётную запись.

→ *Пересмотрено пользователем 2026-10-25 (раздел 10):* параметра глубины нет. Синхронизация
всегда забирает всё, а затем инкрементально догружает изменения.

→ *Пересмотрено пользователем 2026-10-25 (раздел 10):* SQLite нет. Блокировка — замок записи
Lucene, ход синхронизации — в `sync-status.json`, курсоры — в `folders.json` (раздел 6.6).

### 5.3. Умный поиск («RAG на минималках»)

- **BM25 по умолчанию**, без внешних зависимостей. Индексируются: тема, отправитель/получатели,
  тело (текст из HTML), извлечённый текст вложений, имена файлов.
- **Русская морфология** обязательна (стемминг / лемматизация), иначе поиск по-русски
  будет слабым.
- **Эмбеддинги — опционально**: локальная модель (ONNX / Ollama) или внешний API. Гибридное
  ранжирование (BM25 + kNN, например RRF).
- Чанкинг длинных писем и вложений; ответ поиска — сниппеты + идентификаторы для
  последующего `getMessage` / `getAttachment`.
- Кандидаты на движок: **Apache Lucene** (BM25 + HNSW-векторы в одном движке, нативно для
  Java, есть `RussianAnalyzer`) или **SQLite FTS5** (+ расширение для векторов). Решить.

→ *Решено 2026-10-24 (раздел 10, П9, П12):* поиск — Lucene 10.x; русский текст —
`RussianAnalyzer`, английский — отдельное поле, адреса, идентификаторы и имена файлов — без
стемминга. Морфологию проверить своим контрольным набором запросов, при плохих результатах
сравнить с Hunspell. Метаданные и состояние синхронизации — в SQLite (раздел 6). Эмбеддинги — не в
MVP; когда понадобятся — `multilingual-e5-base` (или `-small`) через ONNX Runtime внутри JVM.

→ *Пересмотрено пользователем 2026-10-25 (раздел 10):* SQLite нет; метаданные хранятся в том же
индексе Lucene, курсоры — в `folders.json` (разделы 6.4–6.5).

### 5.4. Фильтр чувствительных данных

Слой между данными и MCP-ответом. Пример: вместо настоящего пароля LLM видит
`[скрыто: пароль — см. письмо от 12.03.2026 от ivanov@…, id=…]`.

Что ловить (черновик): пароли («пароль:», «password:», «pwd»), токены и API-ключи, приватные
ключи, номера карт, паспортные данные, строки подключения. Детекторы — регулярки + правила,
настраиваемые пользователем; позже, возможно, ML.

Важные вопросы:

- **Где применять фильтр**: только на выходе в MCP или ещё до индексации? Если эмбеддинги
  считаются внешним API — фильтровать обязательно **до** отправки текста.
- **Обход через файлы**: если клиент имеет доступ к файловой системе, он может прочитать
  оригинал вложения по `localPath` в обход фильтра. Варианты: хранить отдельно
  «очищенную» копию извлечённого текста и отдавать путь к ней; оригиналы — в отдельном каталоге;
  явно документировать ограничение.
- Отчёт о сработках фильтра (сколько и чего скрыто) — без самих значений.

→ *Решено 2026-10-24 (раздел 10, П11, П13):* фильтр работает **и до индекса, и на выходе**.
Извлечённый текст фильтруется и хранится отдельно; индекс и фрагменты поиска строятся из него;
каждый ответ инструмента и ресурса проверяется повторно. Оригиналы (`.eml`, вложения) — только на
диске; `localPath` модели — только на отфильтрованный текст. Смена детекторов требует
переиндексации. В MVP — 15 детекторов из RT-08, замена вида `[скрыто: пароль; письмо=…; дата=…]`
без длины и хвоста значения; проверка на синтетическом наборе примеров.

→ *Пересмотрено пользователем 2026-10-25 (раздел 10):* фильтр откладывается. На диск и в индекс
всё складывается как есть, без фильтрации. Фильтр будет применяться только при отдаче данных
модели и только опционально.

### 5.5. Письма как MCP-ресурсы

После скачивания письмо/вложение регистрируется как ресурс, например `mail://message/<id>`,
`mail://attachment/<id>`. Плюс: клиент может прикрепить письмо в контекст как документ.
Проверить, как ресурсы поддерживают целевые клиенты (Claude Code и др.).

→ *Решено 2026-10-24 (раздел 10, П13):* основной доступ — инструменты с чтением частями
(`truncated`, `nextOffset`); ресурсы и `resource_link` — дополнение через тот же фильтр;
подписки отложить. URI ресурсов включают соединение: `mail://<connection>/message/<id>`.

### 5.6. Режимы работы

- По умолчанию — **только чтение** (в отличие от redmine-mcp-server, где запись включена по
  умолчанию). При выключенной записи инструменты записи не регистрируются вовсе.
- Запись — отдельный флаг (например, `MAIL_MCP_WRITE_ENABLED=true`), начинать с черновиков,
  а не с прямой отправки. Дополнительно — разрешение записи на уровне соединения (раздел 5.7):
  например, писать можно из личного ящика, но не из рабочего.
- → *Решено 2026-10-24 (раздел 10, П4):* «только чтение» — на уровне протокола. В EWS —
  разрешённый список из 10 операций чтения (research.md 1.2); в IMAP — `EXAMINE` и `BODY.PEEK`.
  Никаких служебных флагов в ящике; учёт «уже показанного» — локально.

### 5.7. Список соединений (по образцу jdbc-mcp-server)

Почтовых ящиков несколько: рабочий Exchange, Gmail, Mail.ru. Поэтому сервер с самого начала
работает со **списком соединений**, как jdbc-mcp-server со списком баз.

**Как это сделано в jdbc-mcp-server** (`docs/connections.md`, пакет `connection/`):

- Все базы — в одном файле `connections.json` в каталоге данных
  (`%USERPROFILE%\.jdbc-mcp-server\`). Путь меняется переменными `JDBC_MCP_CONNECTIONS_FILE`
  и `JDBC_MCP_DATA_DIR`. Файл читается один раз при старте; после правки — перезапуск.
- Ключ записи — **имя соединения** (`[A-Za-z0-9._-]+`, необязательный суффикс `@стенд`,
  до 64 символов). Имя — это и аргумент инструментов, и имя каталога локальных данных
  (`<dataDir>/<имя>/`), и часть URI ресурсов.
- **Соединения по умолчанию нет**: каждый инструмент первым аргументом принимает `connection`.
  Неизвестное имя → ошибка со списком доступных. Набор инструментов один на все соединения.
- `listConnections` читает только конфигурацию (работает, даже если сервер недоступен) и
  показывает `configError` для записей, которые нельзя использовать.
- **Ленивая инициализация и изоляция**: соединение создаётся при первом обращении, со своей
  блокировкой; недоступная база не мешает остальным; ошибка инициализации не кэшируется.
- Поле `description` — единственное, что объясняет агенту, *зачем* это соединение.
- **Секреты** — в файле, а не в переменных окружения и не в конфигурации MCP-клиента: эти
  места агент и так читает. В любом строковом поле работают подстановки `${VAR}`; незаданная
  переменная — ошибка старта, а не пустой пароль. Права на файл — только владельцу (`icacls`).
  Документация честно оговаривает: процесс от имени того же пользователя (агент с доступом к
  shell) файл прочитать всё равно может — это защита от случайного, а не от злонамеренного.
- В логах каждая запись внутри вызова инструмента помечена именем соединения (MDC).

**Как это ложится на почту.** Пример `%USERPROFILE%\.mail-mcp-server\connections.json`
(с комментариями — только для иллюстрации; значения — заглушки):

```jsonc
{
  "connections": {
    "work": {
      "type": "ews",
      "url": "https://webmail.example.com/EWS/Exchange.asmx",
      "auth": "ntlm",                       // ntlm | basic
      "username": "user",
      "password": "…",
      "description": "Рабочая почта, Exchange 2013"
    },
    "gmail": {
      "type": "imap",
      "host": "imap.gmail.com", "port": 993, "tls": true,
      "auth": "app-password",               // app-password | oauth2
      "username": "user@gmail.com",
      "password": "${GMAIL_APP_PASSWORD}",
      "description": "Личная почта Gmail"
    },
    "mailru": {
      "type": "imap",
      "host": "imap.mail.ru", "port": 993, "tls": true,
      "auth": "app-password",
      "username": "user@mail.ru",
      "password": "…",
      "description": "Личная почта Mail.ru"
    }
  }
}
```

Черновик полей соединения:

| Поле | Назначение |
|---|---|
| `type` | `ews` или `imap`; выбирает реализацию источника |
| `url` / `host`, `port`, `tls` | Адрес сервера (EWS — URL, IMAP — хост и порт) |
| `auth`, `username`, `password`, `domain` | Способ входа и учётные данные; `${VAR}` разрешены |
| `description` | Что это за ящик — для агента |
| `folders` | Какие папки синхронизировать и индексировать (включить/исключить), с какой даты |
| `index` | Включён ли локальный индекс, эмбеддинги для этого ящика |
| `redaction` | Профиль фильтра секретов (например, для рабочего ящика строже) |
| `writeEnabled` | Разрешена ли запись через это соединение (действует, только если запись включена глобально) |
| лимиты | Максимальный размер письма, вложения, число писем за одну синхронизацию |

**Что меняется в проекте:**

- **Общий формат — MIME.** EWS отдаёт `MimeContent`, IMAP — `BODY[]`. Значит, у всех источников
  на выходе один `.eml`, один парсер, один формат хранения и один пайплайн извлечения вложений.
  Различаются только доступ и синхронизация.
- **Интерфейс источника** (`MailSource`): список папок, изменения с момента прошлой синхронизации,
  получить письмо (MIME), получить вложение, поиск на стороне сервера. Реализации: `EwsSource`,
  `ImapSource`. Gmail и Mail.ru — одна реализация IMAP с разными настройками.
- **Синхронизация зависит от типа**: EWS — `SyncFolderItems` со sync state; IMAP — `UIDVALIDITY`
  + `UID`, при поддержке сервером — `CONDSTORE`/`QRESYNC`.
- **Особенности Gmail**: метки вместо папок — одно письмо видно в нескольких «папках», а
  «Вся почта» содержит всё. Нужна дедупликация по `X-GM-MSGID`, цепочки — по `X-GM-THRID`.
- **Каталог данных — по соединению**: `<dataDir>/<connection>/messages/…`, `index/`, `sync/`.
- **Идентификатор письма** в ответах — пара «соединение + ключ письма»; URI ресурсов тоже
  включает соединение: `mail://<connection>/message/<id>`.
- **Учётные данные — только в файле соединений**, вне репозитория и вне рабочей папки проекта.
  Это заодно закрывает вопрос из раздела 3: реальные хосты и логины живут в этом файле, а не в
  документации. Ни один инструмент не возвращает секреты из конфигурации; фильтр секретов (5.4)
  дополнительно страхует ответы.

**Чем почта отличается от баз** (над чем подумать):

- В jdbc-mcp-server соединения по умолчанию нет, и это правильно для баз. Для почты
  естественен поиск **по всем ящикам сразу** («найди письмо про договор, не помню где»). Вариант:
  инструменты чтения требуют `connection`, а `searchLocal` принимает список соединений или
  «все».
  → *Решено 2026-10-24 (раздел 10, вопрос 12):* как в jdbc-mcp-server — **каждый** инструмент,
  включая `searchLocal`, требует `connection`; поиска по всем ящикам одним вызовом нет.
- Gmail с OAuth2 требует хранить refresh-токен. Хранить его в каталоге данных соединения с теми же
  правами, что и файл соединений; первичное получение токена — отдельная команда, не инструмент MCP.
  → *Реализовано 2026-10-25 по просьбе пользователя:* `auth: oauth2`, `oauthClientFile` с путём к
  Google Desktop client JSON вне репозитория, команда `gmail-oauth <соединение>` с PKCE S256,
  проверкой `state` и локальным callback. Refresh-токен — в
  `<dataDir>/<connection>/oauth/google-tokens.json` с правами владельца и атомарной заменой,
  доступ к обновлению — под файловой блокировкой. Access-токен остаётся в памяти; IMAP использует
  только XOAUTH2, без повторов и перехода к паролю. Отозванный/истёкший refresh-токен требует
  нового пользовательского запуска команды. Инструкция —
  [gmail-oauth-agent.md](gmail-oauth-agent.md). Область доступа IMAP — `https://mail.google.com/`;
  разрешение широкое, чтение ограничивается клиентом на уровне команд протокола.
  → *Уточнение пользователя 2026-10-25:* свой Gmail пока не подключать, локальная конфигурация —
  только `work` и `mailru`; возможность подключения Gmail и OAuth2 сохраняется.
  → *Уточнение структуры 2026-10-25:* реализация Google находится в `source/oauth/google/`,
  общие `OAuthLoopbackReceiver` и `OAuthException` — в `source/oauth/`. Общий пакет не зависит от
  провайдера; другие реализации OAuth будут добавляться соседними подпакетами по необходимости.
- Более сильная защита секретов, чем «файл с правами владельца»: значения из Windows Credential
  Manager (например, `${cred:mail-work}`) или зашифрованные DPAPI. Возможно, позже.

## 6. Архитектура

Переписано 2026-10-25 по решениям пользователя (раздел 10): без SQLite, без фильтра на входе,
без параметра глубины, без отдельного процесса разбора. Прежний черновик раздела — в истории
git до коммита `4dbdb9d`; принятые тогда решения остаются в журнале (раздел 10), пересмотренные
там отмечены.

Неизменное: Java 25, Spring Boot `4.2.0-RC1`, Spring AI `2.1.0-RC1` (П6); только stdio, ничего,
кроме JSON-RPC, в `System.out`; EWS — свой клиент на StAX с NTLM (П1), IMAP — Angus Mail (П3);
только чтение на уровне протокола (П4); каждый инструмент принимает `connection`.

### 6.1. Принципы

1. **Источник истины локально — `.eml`, как его отдал сервер.** Письмо скачивается один раз и
   больше не меняется. Всё остальное (метаданные, текст, индекс) выводится из `.eml`.
2. **Один индекс Lucene на соединение — и каталог, и поиск.** В нём по документу на письмо:
   ссылка на сервере, папка, состояние, заголовки, текст. Отдельной базы нет.
3. **Курсоры синхронизации — в `folders.json`.** Маленький файл на соединение: папки и
   непрозрачный курсор каждой.
4. **Синхронизируется всё**, затем инкрементально — средствами сервера: в IMAP `UIDVALIDITY` и
   UID, в EWS `SyncFolderItems` со `SyncState`.
5. **Всё хранится как есть.** Фильтр секретов, если появится, применяется только к ответу модели
   и только по настройке (раздел 5.4).
6. **Проще — лучше.** Единственные пороги: размер письма при скачивании (64 MiB, уже в клиентах),
   размер вложения для извлечения текста, длина ответа инструмента.

### 6.2. Поток данных

```
MailSource (EWS | IMAP)
  folders() · changes(folder, cursor, known) · download(folder, ref, target)
        │
        ▼
SyncRunner — один запуск на соединение, в фоне, только в процессе, взявшем IndexWriter
  для каждой папки:
    1. changes → новые ссылки, удалённые ссылки, новый курсор (или «папку сбросить»)
    2. удалённые: документ из индекса и .eml с диска
    3. новые, пачками по 100: скачать в messages/<key>.eml → разобрать (MimeReader)
       → документ в индекс (state=INDEXED или FAILED с причиной) → commit
    4. после папки: курсор в folders.json
        │
        ▼
Инструменты: читают folders.json, индекс и .eml; в сеть не ходят
```

Сбой посреди папки: курсор не сдвинут, следующий запуск снова получает те же ссылки и
пропускает уже имеющиеся в индексе. `.eml` без документа в индексе удаляются в начале запуска.
Индекс потерян или повреждён — полная синхронизация заново (это кэш, а не данные пользователя).

### 6.3. Пакеты и типы

| Пакет | Что внутри |
|---|---|
| `source/` | `MailSource`, `RemoteFolder`, `FolderChanges`; реализации в `source/imap/` и `source/ews/` |
| `model/` | `MailMessage`, `Address`, `AttachmentInfo`, `MessageCard`, `LocalFolder` — каждая запись в своём файле |
| `mime/` | `MimeReader`: `.eml` → `MailMessage` |
| `store/` | `MailStore`: пути `.eml`, чтение и атомарная запись `folders.json`, `sync-status.json` |
| `index/` | `MailIndex`: поля документа, запись и чтение Lucene |
| `sync/` | `SyncRunner` (один запуск), `SyncService` (фон, статус) |
| `tools/`, `api/` | MCP-инструменты и их записи-ответы; `model/` наружу напрямую не отдаётся |

```java
public interface MailSource extends AutoCloseable {
    List<RemoteFolder> folders();
    /** cursor == null: с начала. known: ссылки папки, уже лежащие в индексе. */
    FolderChanges changes(RemoteFolder folder, String cursor, Set<String> known);
    /** Пишет сырой MIME в target (через временный файл), возвращает размер и SHA-256. */
    Downloaded download(RemoteFolder folder, String ref, Path target);
}
record RemoteFolder(String remoteId, String path) { }
record FolderChanges(List<String> added, List<String> removed, String cursor, boolean reset) { }
record Downloaded(long size, String sha256) { }
```

Ссылка `ref` для IMAP — UID строкой, для EWS — `ItemId`. `removed` IMAP вычисляет сам как
`known` минус `UID SEARCH ALL`; EWS берёт удаления из ответа `SyncFolderItems`. `reset = true`,
когда курсор недействителен (сменился `UIDVALIDITY`, EWS отверг `SyncState`): синхронизатор
удаляет все письма папки и скачивает её заново.

`MailMessage` (результат `MimeReader`): тема, `from`/`to`/`cc`/`replyTo` (`Address`: имя, адрес),
дата, `Message-ID`, `In-Reply-To`, `References`, текст тела, тип исходного тела (plain/html),
список `AttachmentInfo` (номер, имя, тип, размер). Ключ письма `key` — UUID, выдаётся при
скачивании (П2). Перемещение письма — удаление и добавление, ключ при этом новый.

### 6.4. Раскладка на диске

```
%USERPROFILE%\.mail-mcp-server\
  connections.json
  logs/
  <connection>/
    folders.json        — папки и курсоры
    sync-status.json    — ход текущего или последнего запуска (читают все процессы)
    messages/<key>.eml  — оригиналы, как скачаны
    index/              — Lucene
    attachments/<key>/<n>__<имя>  — вложения, извлечённые по запросу getAttachment
```

```json
{
  "folders": [
    { "key": "f1", "remoteId": "INBOX", "path": "INBOX", "cursor": "1712345678:48211" },
    { "key": "f2", "remoteId": "AAMkAD…", "path": "Входящие/Проекты", "cursor": "H4sIAAAA…" }
  ]
}
```

Курсор понимает только источник: IMAP — `UIDVALIDITY:последний UID`, EWS — `SyncState`.
Файл пишется во временный и переименовывается.

### 6.5. Документ индекса

| Поле | Как хранится | Зачем |
|---|---|---|
| `key` | строка, хранится | ключ письма |
| `ref` | строка, хранится, уникальна | `<ключ папки>/<ref>`: поиск при удалении и пропуск уже скачанных |
| `folder` | строка, хранится | фильтр `listMessages` |
| `state`, `error` | строка, хранится | `INDEXED` или `FAILED` и короткая причина |
| `size`, `sha256`, `downloadedAt` | хранится | сведения об оригинале |
| `date` | число, хранится, сортировка | сортировка и фильтр по дате |
| `subject`, `from`, `to`, `cc` | текст, хранится | карточки и поиск |
| `messageId`, `inReplyTo`, `references` | строки, хранятся | цепочки писем |
| `body` | текст, хранится | поиск и фрагменты |
| `attachmentNames` | текст, хранится | карточки и поиск по имени |
| `attachmentText` | текст, не хранится | поиск по содержимому вложений (шаг 7.6) |

Анализатор текстовых полей — `RussianAnalyzer` (П9). Смена анализатора или полей —
переобработка: проход по документам, повторный разбор `.eml` по `key`, обновление документа с
сохранением `ref`, `folder`, `key`. В сеть при этом не ходим.

### 6.6. Синхронизация

- **Запуск** — только по запросу: инструмент `sync` или команда `mail-sync <connection>`.
  Инструмент запускает работу в фоне и сразу отвечает; ход — в `sync-status.json`
  (папка, сколько скачано/удалено/с ошибкой, время, ошибка запуска).
- **Один писатель.** Запуск открывает `IndexWriter`; замок Lucene (`write.lock`) не даёт второму
  процессу синхронизировать то же соединение — тот отвечает «синхронизация идёт в другом
  процессе». Читают все процессы; читатель переоткрывает индекс после коммита.
- **Одна сессия на запуск.** Вход в ящик — один раз за запуск. Ошибка входа или обрыв
  соединения останавливает запуск без повторов (раздел 5.2). Ошибка одного письма (больше
  64 MiB, не разбирается) — документ `FAILED` с причиной, запуск идёт дальше; повторно такое
  письмо не скачивается.
- **Какие папки.** IMAP: все папки, кроме `\Noselect`, `\Trash`, `\Junk`, `\Drafts` (атрибуты
  SPECIAL-USE). EWS: папки класса `IPF.Note` под корнем ящика, кроме «Удалённых», «Нежелательной
  почты», «Черновиков», «Исходящих» и поисковых. Новые папки появляются, пропавшие удаляются со
  всеми письмами.
- **Флаги** (прочитано, важное) и метки Gmail в MVP не синхронизируются.

### 6.7. Разбор `.eml`

`MimeReader` — Angus Mail, который уже есть в сборке: `new MimeMessage(session,
new SharedFileInputStream(file))` читает файл лениво. Правила:

- тело: первая часть `text/plain` вне вложений; если её нет — первая `text/html`, переведённая в
  текст через jsoup; кодировка — заявленная в письме, без угадывания;
- вложение: часть с `Content-Disposition: attachment` или с именем файла; вложенное письмо
  (`message/rfc822`), MSG, TNEF, ZIP — обычные вложения, внутрь не разбираются;
- ошибка разбора — исключение; синхронизатор помечает письмо `FAILED`, `.eml` остаётся.

### 6.8. Инструменты

| Инструмент | Что делает |
|---|---|
| `listConnections` | есть |
| `sync`, `syncStatus` | запуск синхронизации в фоне; ход и итог последнего запуска |
| `listFolders` | папки из `folders.json` с числом писем из индекса |
| `listMessages` | карточки писем папки по дате, от новых, `offset`/`limit` |
| `getMessage` | заголовки, текст тела частями (`offset`, `nextOffset`), список вложений |
| `getAttachment` | извлекает вложение из `.eml` в `attachments/`, возвращает `localPath` и текст частями |
| `search` | поиск по индексу: карточки и фрагмент |

Карточка (`MessageCard`): `key`, дата, отправитель, тема, есть ли вложения, папка. Поиск на
сервере не нужен: локально лежит всё. Цепочки (`getThread`) — позже, по `references`.

### 6.9. Чего не делаем

Без отдельного решения пользователя (раздел 10) не добавлять:

- общих бюджетов, счётчиков и сроков разбора, отдельного процесса для разбора;
- SQLite или другой базы рядом с индексом;
- кодов диагностики и статусов сверх `INDEXED`/`FAILED` с причиной;
- разбора вложенных писем, MSG, TNEF, ZIP, календарей в MVP;
- фильтра секретов до шага 7.7;
- синхронизации флагов, записи в ящик, автоматических повторов входа;
- защит «на будущее», которых не требует критерий готовности шага.

## 7. Шаги

Каждый шаг заканчивается рабочим результатом, тесты не ходят в сеть (поддельные серверы как в
`ImapClientTest` и `HttpClient5EwsTransportTest`, наборы `testdata/`). Проверку на настоящем
ящике запускает пользователь. Шаг не начинается, пока не принят предыдущий.

### 7.1. `MailSource` и IMAP-источник

- **Сделать:** интерфейс и записи раздела 6.3; `ImapMailSource` поверх `ImapClient`: `folders()`
  с исключениями 6.6, `changes()` по `UIDVALIDITY` и `UID SEARCH`, `download()` через
  `BODY.PEEK[]`. Сейчас `ImapClient.downloadLastMessage` закрывает сессию после каждого письма —
  переделать на одну сессию на весь запуск.
- **Готово, когда:** тест на поддельном IMAP-сервере: папки с атрибутами отфильтрованы;
  первый `changes(null)` отдаёт все UID; второй с курсором — только новые; удалённый UID попадает
  в `removed`; смена `UIDVALIDITY` даёт `reset`; при скачивании нескольких писем вход один;
  флаг `\Seen` не меняется; только команды из разрешённого списка.
- **Не делать:** хранилище, индекс, разбор, EWS.

### 7.2. Хранилище, индекс-каталог и синхронизация IMAP

- **Сделать:** `MailStore` (`folders.json`, `sync-status.json`, пути `.eml`), `MailIndex` с
  полями `key`, `ref`, `folder`, `state`, `error`, `size`, `sha256`, `downloadedAt`;
  `SyncRunner` по разделу 6.2 без разбора (документ — только эти поля); команда
  `mail-sync <connection>` в jar, печатает итог по папкам.
- **Готово, когда:** тест на поддельном сервере: первый запуск скачивает все письма, второй —
  ничего, после добавления — одно, после удаления — удаляет документ и `.eml`; прерванный
  посреди папки запуск при повторе не скачивает уже имеющееся; второй `IndexWriter` на то же
  соединение отказывает. Пользователь запускает `mail-sync mailru` дважды: второй запуск
  ничего не скачивает.
- **Не делать:** разбор MIME, инструменты MCP.

### 7.3. EWS-источник

- **Сделать:** `EwsMailSource`: папки через `FindFolder`, `changes()` через `SyncFolderItems`
  (создания и удаления; прочие изменения пропускаются), `download()` через `GetItem` с MIME.
  Синхронизатор не меняется.
- **Готово, когда:** тест на синтетических ответах EWS: страницы `SyncFolderItems` до
  `IncludesLastItemInRange`, удаления, недействительный `SyncState` → `reset`. Пользователь
  запускает `mail-sync work` дважды; второй запуск ничего не скачивает.
- **Не делать:** операции вне разрешённого списка (П4).

### 7.4. Разбор `.eml` и первые инструменты

- **Сделать:** `MimeReader` и записи `model/` (разделы 6.3, 6.7); разбор в `SyncRunner` и

  `syncStatus`, `listFolders`, `listMessages`, `getMessage`.
- **Готово, когда:** `MimeReader` проходит наборы `testdata/mime` по заголовкам, телу и списку
  вложений (там, где ожидания расходятся с правилами 6.7, тест фиксирует наше поведение);
  инструменты проверены через stdio-тест на синтетическом индексе; `getMessage` отдаёт длинное
  тело частями.
- **Не делать:** поиск, вложения, фильтр.

### 7.5. Поиск

- **Сделать:** `RussianAnalyzer` для текстовых полей, инструмент `search` с карточками и

### 2026-10-24 — вопросы 7, 8, 12: что, когда и как синхронизировать

остался только вопрос 14 — проверка Mail.ru в аккаунте, вместе с остальными проверками со входом

### 2026-10-24 — каркас сервера и спайк EWS (этап 1)

Написан код этапа 1. Сборка: Gradle 9.8.2 с каталогом версий, Java 25, Spring Boot `4.2.0-RC1`,
Spring AI `2.1.0-RC1` (на 2026-10-24 новее в линии 2.1 нет), Apache HttpClient 5.6.5; пакет
`mail.mcp` — без названия компании. Сервер работает только через stdio, логи — в stderr и файл.
Соединения: `connections.json` из `%USERPROFILE%\.mail-mcp-server\` (переопределяется
`MAIL_MCP_DATA_DIR` и `MAIL_MCP_CONNECTIONS_FILE`), подстановки `${VAR}`, типы `ews`/`imap`, поле
`auth`, ленивый реестр, предупреждения о неизвестных ключах; ошибки отдельной записи попадают в
`configError`. Инструмент `listConnections` показывает только конфигурацию, без адресов и секретов.
Клиент EWS: свой SOAP на StAX, разрешённый список из 10 операций чтения, потоковый разбор MIME;
транспорт — HttpClient 5 с явно зарегистрированным NTLM, только одной схемой, без повторов и
перенаправлений; при отклонённом входе — одна попытка. Код из соседних проектов скопирован с
указанием источника (П5). Тесты (66) идут без сети: синтетические ответы EWS и полное рукопожатие
NTLM с локальным поддельным сервером (в Type 3 — логин `user` и пустой домен), сервер проверяется
через stdio в отдельном процессе.

Спайк запускает пользователь: `java -jar build\libs\mail-mcp-server.jar ews-spike <соединение>` —
`GetFolder` для «Входящих», `FindItem` для самого нового письма и `GetItem` с MIME; `.eml`
сохраняется в `<каталог данных>\<соединение>\spike\`, на экран — только счётчики, размер, хэш,
время и число HTTP-запросов. Известный риск (RT-02): если сервер требует Extended Protection,
NTLM из HttpClient не пройдёт; тогда нужен запасной транспорт на `HttpsURLConnection`. Инженерные
документы: [architecture-agent.md](architecture-agent.md), [build-config-agent.md](build-config-agent.md),
[ews-source-agent.md](ews-source-agent.md).

внутреннем переподключении библиотеки. MIME сохраняется с SHA-256, лимитом 64 MiB и удалением
незавершённого файла; имеющийся оригинал не заменяется. Флаги после скачивания запрашиваются
повторно со сбросом кэша Angus. Скачивание завершает одноразовую сессию; жизненный цикл для
будущей синхронизации предстоит расширить с такими же гарантиями входа. Команда для пользователя:
`java -jar build\libs\mail-mcp-server.jar imap-spike gmail` (или другое IMAP-соединение).
Агент в реальные ящики не входил и заполненный `connections.json` не открывал.

Данные: RT-11 — 20 MIME-случаев (включая настоящий MSG с ZIP, TNEF с RTF и Unicode-именем,
проверенные CMS-структуры); RT-12 — 256 примеров для 15 детекторов и 8 смешанных документов;
RT-13 — 48 писем, из них 16 с вложениями, и 80 запросов во всех 14 категориях. Всё выдумано;
приватные материалы OpenSSL остаются только в игнорируемом рабочем каталоге. POI 5.4.1 взят
из существующего кэша для независимой проверки MSG/TNEF. Стандартная библиотека Python
проверила манифесты, 48 JSON-файлов, 68 EML, суммы, хэши, кодировки, вхождения и ожидаемые
замены. Спорные границы и суммы не объявляются принятой политикой фильтра.

Полная сборка `gradlew.bat build` прошла: 80 тестов, из них 79 успешны и 1 ранее отключён.
Парсер, хранилище, индекс и детекторы пока не реализованы. Дальше — пользовательский IMAP-спайк
и реализация локального конвейера на подготовленных данных.

### 2026-10-25 — Gmail OAuth2 готов к пользовательской проверке

По просьбе пользователя реализован альтернативный вход Gmail: команда `gmail-oauth <соединение>`
открывает системный браузер и получает согласие через Google Desktop OAuth с PKCE S256,
случайным `state` и callback только на `127.0.0.1` со случайным портом. Код и токены не печатаются.
Refresh-токен сохраняется с правами владельца в каталоге соединения; access-токен — только в
памяти. Перед IMAP-входом токен обновляется одним запросом, без автоматических повторов,
перенаправлений и повторного открытия браузера; ошибки отзыва требуют нового пользовательского
согласия. Смена refresh-токена сохраняется атомарно, запись защищена файловой блокировкой.

IMAP выбирает только XOAUTH2. Отдельный обработчик обмена исправляет поведение Angus 2.0.5:
на challenge с ошибкой отправляется пустой ответ, как требует Google, вместо повторной отправки
токена. Проверены оба режима: SASL-IR и ответ на начальный запрос сервера. Переход на LOGIN
или пароль при отсутствии XOAUTH2 запрещён перед отправкой.

Сборка проходит: 92 теста, 91 успешен, 1 ранее отключён. Новые проверки используют только
поддельные токены, замену браузера и локальные серверы. Реальный Google-вход агент не запускал;
пользовательские `connections.json`, OAuth client JSON и токены не открывал. Результат реального
Gmail-спайка остаётся открытым. Новая инструкция — [gmail-oauth-agent.md](gmail-oauth-agent.md).

При проверке актуальных правил Google уточнено: OAuth не требует пароля приложения для Gmail,
но Google Cloud Console требует 2FA у управляющего проектом аккаунта. Проект можно создать
под другим своим аккаунтом с 2FA, добавив нужный ящик в Test users; проверка Google при самом
входе в ящик по-прежнему возможна. Для External/Testing refresh-токен с областью IMAP истекает
через 7 дней. Источники и ограничения зафиксированы в новой инструкции.

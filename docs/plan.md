# mail-mcp-server — план и обсуждение

Рабочий документ для обсуждения идеи. Здесь фиксируем цели, решения, открытые вопросы и ход
обсуждения. Исследование существующих решений и протоколов доступа — в [research.md](research.md).

Статус: **идея / исследование**. Кода пока нет.

## 1. Идея в одном абзаце

Локальный stdio MCP-сервер для нескольких почтовых ящиков — рабочего Exchange, Gmail и Mail.ru, —
сделанный «по образцу» `C:\git\redmine-mcp-server`. Ящики описываются списком соединений, как
базы в `C:\git\jdbc-mcp-server` (раздел 5.7). Сервер даёт AI-агенту (Claude Code, Cursor и т.п.) читать почту,
скачивает письма и вложения в локальную папку, извлекает из вложений текст, строит локальный
поисковый индекс по письмам **и** вложениям («RAG на минималках»: BM25 по умолчанию, эмбеддинги —
опционально) и пропускает всё, что уходит в LLM, через фильтр чувствительных данных.
По умолчанию — только чтение; отправка писем — позже и опционально.

## 2. Зачем своё, если решения уже есть

- Веб-интерфейс OWA (`https://webmail.example.com/owa`) неудобен.
- Нужны свои доработки, которых нет в готовых решениях: фильтр секретов, поиск по вложениям,
  локальный индекс, оформление писем как MCP-ресурсов.
- Есть отработанный образец (redmine-mcp-server): архитектура, пайплайн извлечения текста из
  вложений, снапшоты на диске, ограничения размера ответов.
- Готовые решения всё равно изучаем — для идей и правил (см. [research.md](research.md)).

Наблюдения:

- Два разных хоста: `webmail.example.com` (OWA) и `mail.example.com` (ActiveSync).
  Возможно, это один сервер под двумя именами — надо проверить.
- Раз работает OWA и ActiveSync, скорее всего доступен и **EWS**
  (`/EWS/Exchange.asmx`) — основной кандидат для доступа из кода. Проверить (см. раздел 9).
- Microsoft Graph для чистого on-premise Exchange обычно недоступен.

### 3.1. Проверка эндпоинтов (2026-10-24)

Анонимные запросы `curl` без авторизации, смотрели только заголовки ответа.

| URL (оба хоста: `webmail.` и `mail.example.com`) | Ответ | `WWW-Authenticate` |
|---|---|---|
| `/EWS/Exchange.asmx` | `401 Anonymous Request Disallowed` | `Negotiate`, `NTLM`, `Basic` |
| `/autodiscover/autodiscover.xml` | `401 Anonymous Request Disallowed` | `Negotiate`, `NTLM`, `Basic` |
| `/Autodiscover/Autodiscover.svc` | `401 Anonymous Request Disallowed` | `Negotiate`, `NTLM`, `Basic` |
| `/Microsoft-Server-ActiveSync` | `401 Unauthorized` | только `Basic` |
| `/owa/` | `302` → `/owa/auth/logon.aspx` (форма входа) | — |

Общие заголовки: `Server: Microsoft-IIS/8.5`, `X-OWA-Version: 15.0.1497.x`, одинаковый
`X-FEServer` на обоих хостах.

DNS и TLS:

- `webmail.example.com` и `mail.example.com` указывают на **один IP** и отвечают одним и тем
  же фронтендом, то есть это один сервер под двумя именами.
- Сертификат — wildcard на домен компании от публичного удостоверяющего центра.
- `autodiscover.example.com` **не резолвится**, SRV-записи `_autodiscover._tcp.example.com`
  нет. Autodiscover доступен только по пути `/autodiscover/...` на основных хостах.

Выводы:

- **EWS доступен из интернета** — основной кандидат на протокол подтверждён.
- **Версия: Exchange 2013** (сборка 15.0.1497.x — это CU23, последнее накопительное обновление
  2013; IIS 8.5 — Windows Server 2012 R2). Поддержка Exchange 2013 у Microsoft закончилась
  в апреле 2023 года. Значит, новых API не будет, ориентируемся на EWS схемы Exchange 2013
  (`Exchange2013_SP1`).
- **Аутентификация для EWS**: Basic по HTTPS (самый простой вариант для Java), NTLM и Negotiate
  (Kerberos/NTLM) тоже предложены. Kerberos/SSO возможен только с доменной машины.
- Autodiscover в клиенте делать не обязательно: URL EWS можно задавать в конфигурации явно.
- Пока не проверено: работает ли Basic из кода, лимиты троттлинга EWS, включены ли IMAP/SMTP.

### 3.2. Вход с учётными данными (2026-10-24)

- **Браузер: успех.** `https://webmail.example.com/EWS/Exchange.asmx`, доменный логин и
  пароль в окне браузера. Машина не в домене, поэтому браузер, скорее всего, вошёл через
  NTLM (через Negotiate). Значит, учётная запись имеет доступ к EWS.
- **Скрипт [scripts/ews-login-check.ps1](../scripts/ews-login-check.ps1), первая версия: неуспех.**
  Пробовал только `user@example.com` и `example.com\user` (Basic и NTLM).
  Механика скрипта проверена анонимным запросом: запрос уходит, ответ `401` разбирается.
  Причина — формат логина. В скрипт добавлены логин без домена (`user`) и метод `Negotiate`.
- **Скрипт, вторая версия: успех.** `-Logins user -Methods NTLM`, одна попытка:

  | Метод | Логин | HTTP | Результат | Папка | Всего | Непрочитано |
  |---|---|---|---|---|---|---|
  | NTLM | `user` | `200 OK` | `Success` / `NoError` | Входящие | 1987 | 691 |

Выводы:

- **Рабочая схема входа из кода: NTLM, логин без домена (`user`).** Домен подставляет
  сервер. Форматы `user@example.com` и `example.com\user` в первой версии не
  прошли (точный ответ по каждому не сохранился).
- `RequestServerVersion Exchange2013_SP1` принимается, кириллица в ответе (`Входящие`)
  приходит корректно в UTF-8.
- Объём: во «Входящих» ~2000 писем — для локального индекса это немного; общий объём по всем
  папкам ещё предстоит оценить.
- **Следствие для Java.** Встроенный `java.net.http.HttpClient` NTLM не умеет. Варианты:
  Apache HttpClient 5 (NTLM есть, но помечен устаревшим), реализация NTLM в `ews-java-api`
  (на Apache HttpClient 4), либо Basic, если он работает. Basic для EWS пока не проверен.

## 4. Цели и не-цели

### Цели (MVP и ближайшие этапы)

0. Несколько почтовых ящиков сразу: список соединений в отдельном файле, у каждого свой тип
   (EWS, IMAP), свои свойства и учётные данные (раздел 5.7).
1. Чтение почты: папки, списки писем, письмо целиком, цепочки (threads).
2. Вложения: скачивание в локальную папку по запросу, извлечение текста (PDF, DOCX, XLSX, PPTX,
   ZIP, txt…), возврат `localPath`/`fileUri` — как `getAttachment` в redmine-mcp-server.
3. Локальное хранилище писем (снапшоты на диске) с инкрементальной синхронизацией.
4. Локальный поиск по теме, телу и тексту вложений: BM25 по умолчанию.
5. Фильтр чувствительных данных между почтой и MCP-ответом.
6. Режим «только чтение» по умолчанию.

### Позже / опционально

7. Эмбеддинги и гибридный поиск (BM25 + векторы).
8. Письма и вложения как MCP-ресурсы.
9. Запись: черновики, ответ, отправка, перемещение, флаги — отдельно включаемый режим.

### Не-цели (пока)

- Полноценный почтовый клиент / замена Outlook.
- Календарь, контакты, задачи Exchange (можно вернуться позже).
- Поддержка всех почтовых систем. Нужны два типа источника: EWS (рабочий Exchange) и IMAP
  (Gmail, Mail.ru). Graph, Gmail API, POP3 и ActiveSync — не сейчас.

## 5. Ключевые идеи (черновик для обсуждения)

### 5.1. Вложения → локальные файлы

Повторяем подход redmine-mcp-server: при обращении к вложению оригинал сохраняется в локальный
каталог, текст извлекается пайплайном парсеров (PDFBox, POI, Tika, pandoc), ответ ограничен
по размеру и «восстанавливаем» (есть путь к оригиналу и способ запросить продолжение).

Отличие от Redmine: в почте вложения бывают вложенными письмами (`.eml`, `.msg`, item
attachments в EWS) — нужен парсер для них (рекурсивно, с ограничением глубины). Также inline-
картинки в HTML-теле (`cid:`) и `winmail.dat` (TNEF).

→ *Решено 2026-10-24 (раздел 10, П10):* разбор писем — Apache James Mime4j в потоковом режиме;
новые парсеры `.eml`, `.msg` (POI HSMF), TNEF (POI HMEF), HTML-тело (jsoup), `.ics` (iCal4j),
распознавание S/MIME без расшифровки. Конвейер из redmine-mcp-server сначала переделать: один
текст на файл, общий лимит глубины и объёма на всю цепочку вложенности, разбор в отдельном
процессе с ограничением памяти и времени. Подробности — research.md, разделы 2 и 6.

### 5.2. Почта — пополняемые данные → локальная база

Почта в основном **дописывается**, а не меняется: новое письмо приходит, старое почти не
редактируется. Поэтому:

- синхронизация инкрементальная (в EWS есть `SyncFolderItems` со sync state);
- письмо можно один раз скачать, распарсить, проиндексировать и больше не трогать;
- индекс — тоже в основном append-only.

Нюансы, которые «пополняемость» нарушают: перемещение между папками, удаление, флаги
прочитано/важно, категории. Нужен стабильный ключ письма: EWS `ItemId` может меняться при
перемещении, поэтому рассмотреть `InternetMessageId` (+ хэш) как основной идентификатор.

→ *Решено 2026-10-24 (раздел 10, П2):* `InternetMessageId` основным ключом **не** берём — он не
гарантирует уникальность экземпляра (research.md 1.2). Ключ письма — локальный UUID в рамках
соединения; отдельно хранятся текущий адрес на сервере (EWS `ItemId`, IMAP `UIDVALIDITY` + `UID`),
`Message-ID` и хэш MIME — для сопоставления при перемещениях. Письмо Gmail хранится один раз по
`X-GM-MSGID`, метки — отдельно.

→ *Решено 2026-10-24 (раздел 10, вопросы 7 и 8):*

- **Что синхронизируется по умолчанию:** все настоящие почтовые папки, кроме «Удалённых», «Спама»,
  «Исходящих», «Черновиков» и поисковых папок; за всю историю. В Gmail — «Вся почта» один раз с
  метками, без «Спама» и «Корзины». Иначе — полями `folders` и `since` в соединении.
- **Когда:** только по запросу — отдельным инструментом синхронизации с параметром глубины:
  «только новое» (по умолчанию), «за N дней», «ещё N писем вглубь истории», «вся история».
  Новые изменения приходят инкрементально; история догружается от новых писем к старым порциями
  и продолжается с места остановки. Инструмент запускает работу в фоне своего экземпляра и сразу
  отвечает; прогресс — через `indexStatus`. Автоматической фоновой синхронизации нет.
- **Удаления и перемещения** приходят той же инкрементальной синхронизацией и учитываются — поиск
  не должен находить удалённые письма.
- **Остальные инструменты** отвечают сразу, только по локальным данным, и показывают покрытие.
- **Вложения:** текст извлекается при синхронизации для вложений до настраиваемого размера
  (например, 20 МБ); у больших — только метаданные, текст при первом обращении; поиск показывает,
  что не проиндексировано.
- **Несколько экземпляров сервера** (разные сессии и клиенты) используют общую базу. Читают все;
  синхронизирует и пишет в индекс только экземпляр, взявший **блокировку соединения** (файловая
  блокировка ОС + запись в SQLite: кто, с какого времени, прогресс). Остальные отвечают «идёт в
  другом экземпляре» и продолжают читать; читатели Lucene переоткрывают индекс после записи.
  Блокировка ОС снимается сама, если процесс упал.
- **Ошибка входа** останавливает синхронизацию соединения без повторов до перезапуска или правки
  конфигурации — иначе устаревший пароль быстро заблокирует доменную учётную запись.

### 5.3. Умный поиск («RAG на минималках»)

- **BM25 по умолчанию**, без внешних зависимостей. Индексируются: тема, отправитель/получатели,
  тело (текст из HTML), извлечённый текст вложений, имена файлов.
- **Русская морфология** обязательна (стемминг / лемматизация), иначе поиск по-русски
  будет слабым.
- **Эмбеддинги — опционально**: локальная модель (ONNX / Ollama) или внешний API. Гибридное
  ранжирование (BM25 + kNN, например RRF).
- Чанкинг длинных писем и вложений; ответ поиска — сниппеты + идентификаторы для
  последующего `getMessage` / `getAttachment`.
- Кандидаты на движок: **Apache Lucene** (BM25 + HNSW-векторы в одном движке, нативно для
  Java, есть `RussianAnalyzer`) или **SQLite FTS5** (+ расширение для векторов). Решить.

→ *Решено 2026-10-24 (раздел 10, П9, П12):* поиск — Lucene 10.x; русский текст —
`RussianAnalyzer`, английский — отдельное поле, адреса, идентификаторы и имена файлов — без
стемминга. Морфологию проверить своим контрольным набором запросов, при плохих результатах
сравнить с Hunspell. Метаданные и состояние синхронизации — в SQLite (раздел 6). Эмбеддинги — не в
MVP; когда понадобятся — `multilingual-e5-base` (или `-small`) через ONNX Runtime внутри JVM.

### 5.4. Фильтр чувствительных данных

Слой между данными и MCP-ответом. Пример: вместо настоящего пароля LLM видит
`[скрыто: пароль — см. письмо от 12.03.2026 от ivanov@…, id=…]`.

Что ловить (черновик): пароли («пароль:», «password:», «pwd»), токены и API-ключи, приватные
ключи, номера карт, паспортные данные, строки подключения. Детекторы — регулярки + правила,
настраиваемые пользователем; позже, возможно, ML.

Важные вопросы:

- **Где применять фильтр**: только на выходе в MCP или ещё до индексации? Если эмбеддинги
  считаются внешним API — фильтровать обязательно **до** отправки текста.
- **Обход через файлы**: если клиент имеет доступ к файловой системе, он может прочитать
  оригинал вложения по `localPath` в обход фильтра. Варианты: хранить отдельно
  «очищенную» копию извлечённого текста и отдавать путь к ней; оригиналы — в отдельном каталоге;
  явно документировать ограничение.
- Отчёт о сработках фильтра (сколько и чего скрыто) — без самих значений.

→ *Решено 2026-10-24 (раздел 10, П11, П13):* фильтр работает **и до индекса, и на выходе**.
Извлечённый текст фильтруется и хранится отдельно; индекс и фрагменты поиска строятся из него;
каждый ответ инструмента и ресурса проверяется повторно. Оригиналы (`.eml`, вложения) — только на
диске; `localPath` модели — только на отфильтрованный текст. Смена детекторов требует
переиндексации. В MVP — 15 детекторов из RT-08, замена вида `[скрыто: пароль; письмо=…; дата=…]`
без длины и хвоста значения; проверка на синтетическом наборе примеров.

### 5.5. Письма как MCP-ресурсы

После скачивания письмо/вложение регистрируется как ресурс, например `mail://message/<id>`,
`mail://attachment/<id>`. Плюс: клиент может прикрепить письмо в контекст как документ.
Проверить, как ресурсы поддерживают целевые клиенты (Claude Code и др.).

→ *Решено 2026-10-24 (раздел 10, П13):* основной доступ — инструменты с чтением частями
(`truncated`, `nextOffset`); ресурсы и `resource_link` — дополнение через тот же фильтр;
подписки отложить. URI ресурсов включают соединение: `mail://<connection>/message/<id>`.

### 5.6. Режимы работы

- По умолчанию — **только чтение** (в отличие от redmine-mcp-server, где запись включена по
  умолчанию). При выключенной записи инструменты записи не регистрируются вовсе.
- Запись — отдельный флаг (например, `MAIL_MCP_WRITE_ENABLED=true`), начинать с черновиков,
  а не с прямой отправки. Дополнительно — разрешение записи на уровне соединения (раздел 5.7):
  например, писать можно из личного ящика, но не из рабочего.
- → *Решено 2026-10-24 (раздел 10, П4):* «только чтение» — на уровне протокола. В EWS —
  разрешённый список из 10 операций чтения (research.md 1.2); в IMAP — `EXAMINE` и `BODY.PEEK`.
  Никаких служебных флагов в ящике; учёт «уже показанного» — локально.

### 5.7. Список соединений (по образцу jdbc-mcp-server)

Почтовых ящиков несколько: рабочий Exchange, Gmail, Mail.ru. Поэтому сервер с самого начала
работает со **списком соединений**, как jdbc-mcp-server со списком баз.

**Как это сделано в jdbc-mcp-server** (`docs/connections.md`, пакет `connection/`):

- Все базы — в одном файле `connections.json` в каталоге данных
  (`%USERPROFILE%\.jdbc-mcp-server\`). Путь меняется переменными `JDBC_MCP_CONNECTIONS_FILE`
  и `JDBC_MCP_DATA_DIR`. Файл читается один раз при старте; после правки — перезапуск.
- Ключ записи — **имя соединения** (`[A-Za-z0-9._-]+`, необязательный суффикс `@стенд`,
  до 64 символов). Имя — это и аргумент инструментов, и имя каталога локальных данных
  (`<dataDir>/<имя>/`), и часть URI ресурсов.
- **Соединения по умолчанию нет**: каждый инструмент первым аргументом принимает `connection`.
  Неизвестное имя → ошибка со списком доступных. Набор инструментов один на все соединения.
- `listConnections` читает только конфигурацию (работает, даже если сервер недоступен) и
  показывает `configError` для записей, которые нельзя использовать.
- **Ленивая инициализация и изоляция**: соединение создаётся при первом обращении, со своей
  блокировкой; недоступная база не мешает остальным; ошибка инициализации не кэшируется.
- Поле `description` — единственное, что объясняет агенту, *зачем* это соединение.
- **Секреты** — в файле, а не в переменных окружения и не в конфигурации MCP-клиента: эти
  места агент и так читает. В любом строковом поле работают подстановки `${VAR}`; незаданная
  переменная — ошибка старта, а не пустой пароль. Права на файл — только владельцу (`icacls`).
  Документация честно оговаривает: процесс от имени того же пользователя (агент с доступом к
  shell) файл прочитать всё равно может — это защита от случайного, а не от злонамеренного.
- В логах каждая запись внутри вызова инструмента помечена именем соединения (MDC).

**Как это ложится на почту.** Пример `%USERPROFILE%\.mail-mcp-server\connections.json`
(с комментариями — только для иллюстрации; значения — заглушки):

```jsonc
{
  "connections": {
    "work": {
      "type": "ews",
      "url": "https://webmail.example.com/EWS/Exchange.asmx",
      "auth": "ntlm",                       // ntlm | basic
      "username": "user",
      "password": "…",
      "description": "Рабочая почта, Exchange 2013"
    },
    "gmail": {
      "type": "imap",
      "host": "imap.gmail.com", "port": 993, "tls": true,
      "auth": "app-password",               // app-password | oauth2
      "username": "user@gmail.com",
      "password": "${GMAIL_APP_PASSWORD}",
      "description": "Личная почта Gmail"
    },
    "mailru": {
      "type": "imap",
      "host": "imap.mail.ru", "port": 993, "tls": true,
      "auth": "app-password",
      "username": "user@mail.ru",
      "password": "…",
      "description": "Личная почта Mail.ru"
    }
  }
}
```

Черновик полей соединения:

| Поле | Назначение |
|---|---|
| `type` | `ews` или `imap`; выбирает реализацию источника |
| `url` / `host`, `port`, `tls` | Адрес сервера (EWS — URL, IMAP — хост и порт) |
| `auth`, `username`, `password`, `domain` | Способ входа и учётные данные; `${VAR}` разрешены |
| `description` | Что это за ящик — для агента |
| `folders` | Какие папки синхронизировать и индексировать (включить/исключить), с какой даты |
| `index` | Включён ли локальный индекс, эмбеддинги для этого ящика |
| `redaction` | Профиль фильтра секретов (например, для рабочего ящика строже) |
| `writeEnabled` | Разрешена ли запись через это соединение (действует, только если запись включена глобально) |
| лимиты | Максимальный размер письма, вложения, число писем за одну синхронизацию |

**Что меняется в проекте:**

- **Общий формат — MIME.** EWS отдаёт `MimeContent`, IMAP — `BODY[]`. Значит, у всех источников
  на выходе один `.eml`, один парсер, один формат хранения и один пайплайн извлечения вложений.
  Различаются только доступ и синхронизация.
- **Интерфейс источника** (`MailSource`): список папок, изменения с момента прошлой синхронизации,
  получить письмо (MIME), получить вложение, поиск на стороне сервера. Реализации: `EwsSource`,
  `ImapSource`. Gmail и Mail.ru — одна реализация IMAP с разными настройками.
- **Синхронизация зависит от типа**: EWS — `SyncFolderItems` со sync state; IMAP — `UIDVALIDITY`
  + `UID`, при поддержке сервером — `CONDSTORE`/`QRESYNC`.
- **Особенности Gmail**: метки вместо папок — одно письмо видно в нескольких «папках», а
  «Вся почта» содержит всё. Нужна дедупликация по `X-GM-MSGID`, цепочки — по `X-GM-THRID`.
- **Каталог данных — по соединению**: `<dataDir>/<connection>/messages/…`, `index/`, `sync/`.
- **Идентификатор письма** в ответах — пара «соединение + ключ письма»; URI ресурсов тоже
  включает соединение: `mail://<connection>/message/<id>`.
- **Учётные данные — только в файле соединений**, вне репозитория и вне рабочей папки проекта.
  Это заодно закрывает вопрос из раздела 3: реальные хосты и логины живут в этом файле, а не в
  документации. Ни один инструмент не возвращает секреты из конфигурации; фильтр секретов (5.4)
  дополнительно страхует ответы.

**Чем почта отличается от баз** (над чем подумать):

- В jdbc-mcp-server соединения по умолчанию нет, и это правильно для баз. Для почты
  естественен поиск **по всем ящикам сразу** («найди письмо про договор, не помню где»). Вариант:
  инструменты чтения требуют `connection`, а `searchLocal` принимает список соединений или
  «все».
  → *Решено 2026-10-24 (раздел 10, вопрос 12):* как в jdbc-mcp-server — **каждый** инструмент,
  включая `searchLocal`, требует `connection`; поиска по всем ящикам одним вызовом нет.
- Gmail с OAuth2 требует хранить refresh-токен. Хранить его в каталоге данных соединения с теми же
  правами, что и файл соединений; первичное получение токена — отдельная команда, не инструмент MCP.
- Более сильная защита секретов, чем «файл с правами владельца»: значения из Windows Credential
  Manager (например, `${cred:mail-work}`) или зашифрованные DPAPI. Возможно, позже.

## 6. Архитектура (черновик)

Берём за основу redmine-mcp-server:

- Java 25, Spring Boot 4, Spring AI MCP server, Gradle 9 с version catalog.
  → *Решено 2026-10-24 (П6):* Spring Boot `4.2.0-RC1`, Spring AI `2.1.0-RC1` (линия 2.1 —
  осознанный выбор; с выходом `2.1.0` переходим на неё).
- Только stdio-транспорт, никакого вывода в `System.out`, логи в stderr/файл.
- Слои: `tools/ → service/ → client/` (+ `extraction/`, `index/`, `redaction/`, `store/`);
  `api/` — стабильные MCP-записи, модели клиента наружу не выходят.
- Ограниченные и восстанавливаемые ответы (`nextOffset`, идентификаторы, `localPath`).
- → *Решено 2026-10-24:* источник EWS — свой тонкий SOAP-клиент на StAX, транспорт за
  интерфейсом, первым — Apache HttpClient 5 с явно включённым NTLM, запасной —
  `HttpsURLConnection` (П1). Источник IMAP для Gmail и Mail.ru — Angus Mail (П3). Код из
  redmine-mcp-server и jdbc-mcp-server копируем с адаптацией, с записью источника и коммита (П5).
  В поиске и списках — короткие карточки, полное письмо и вложения — отдельными вызовами; у
  вложений раздельные лимиты ответа, диска и разбора; поиск показывает, что уже проиндексировано
  (П7).

```
┌─────────────┐  stdio  ┌──────────────────────────────────────────┐   EWS   ┌──────────┐
│  AI-агент   │ <-----> │ mail-mcp-server                          │ ------> │ Exchange │
│             │         │  tools → service → source (EWS / IMAP)   │         └──────────┘
│             │         │   ├─ connections (connections.json)      │   IMAP  ┌──────────┐
│             │         │   ├─ store (снапшоты на диске)           │ ------> │ Gmail    │
│             │         │   ├─ extraction (вложения)               │         └──────────┘
│             │         │   ├─ index (BM25 [+ векторы])            │   IMAP  ┌──────────┐
│             │         │   └─ redaction (фильтр секретов)         │ ------> │ Mail.ru  │
└─────────────┘         └──────────────────────────────────────────┘         └──────────┘
```

Черновик раскладки на диске (по аналогии со снапшотами задач Redmine и каталогами соединений
jdbc-mcp-server):

```
%USERPROFILE%\.mail-mcp-server\
  connections.json      — список соединений с учётными данными (права только владельцу)
  logs/
  <connection>/
    messages/<messageKey>/
      message.json      — метаданные и тело (нормализованные)
      message.eml       — оригинал (MIME)
      attachments/<n>__<filename>
    index/              — поисковый индекс
    sync/               — состояние синхронизации по папкам
```

→ *Решено 2026-10-24 (П9, П11):* метаданные, текущие адреса на сервере, метки Gmail, состояние
синхронизации и разбора — в SQLite, один файл на соединение (вместо `message.json` и `sync/`);
Lucene — только поиск, его можно перестроить заново. Обновлённый черновик раскладки:

```
%USERPROFILE%\.mail-mcp-server\
  connections.json
  logs/
  <connection>/
    store.db            — SQLite: письма, адреса на сервере, метки, состояние синхронизации и разбора
    messages/<uuid>/
      message.eml       — оригинал (MIME), модели не отдаётся
      attachments/<n>__<filename>   — оригиналы вложений, модели не отдаются
      text/             — отфильтрованный извлечённый текст (на него указывает localPath)
    index/              — Lucene, строится из отфильтрованного текста
```

Черновой набор инструментов (только чтение). Все, кроме `listConnections`, принимают
`connection`; для `searchLocal` — см. раздел 5.7.

| Инструмент | Назначение |
|---|---|
| `listConnections` | Настроенные ящики: имя, тип, описание, состояние, ошибка конфигурации; без секретов |
| `listFolders` | Дерево папок с числом писем / непрочитанных |
| `listMessages` | Письма папки с фильтрами (дата, отправитель, непрочитанные), пагинация |
| `getMessage` | Письмо целиком: заголовки, тело, список вложений |
| `getThread` | Цепочка писем (conversation) |
| `getAttachment` | Скачать вложение локально, вернуть `localPath` + извлечённый текст |
| `searchMail` | Поиск на стороне почтового сервера (EWS `FindItem` / IMAP `SEARCH`) |
| `searchLocal` | Поиск по локальному индексу (BM25 / гибрид), по письмам и вложениям, по одному или нескольким ящикам |
| `syncFolder` / `indexStatus` | Запуск инкрементальной синхронизации, состояние индекса |

→ *Решено 2026-10-24 (вопросы 8 и 12):* `searchLocal` — по одному соединению. Синхронизация —
один инструмент с параметром глубины (раздел 5.2), запускается в фоне и сразу отвечает;
`indexStatus` показывает покрытие, прогресс и экземпляр, который сейчас синхронизирует.

Открытый вопрос — **переиспользование кода** из redmine-mcp-server (`extraction/`,
`compression/`, логирование) и jdbc-mcp-server (`connection/`: загрузка файла, `${VAR}`,
реестр с ленивой инициализацией): копировать или вынести в общую библиотеку.
→ *Решено 2026-10-24 (П5):* копировать с адаптацией; общую библиотеку не выделять до появления
общего устойчивого ядра.

### 2026-10-24 — вопросы 7, 8, 12: что, когда и как синхронизировать

Закрыты последние открытые вопросы. По умолчанию — все почтовые папки, кроме мусорных, за всю
историю. Пользователь указал, что экземпляров сервера может быть запущено несколько из разных
сессий при одной общей базе; поэтому автоматической синхронизации нет: инструменты отвечают
сразу по локальным данным и показывают покрытие, а синхронизацию запускает отдельный инструмент с
параметром глубины. Пишет только экземпляр, взявший блокировку соединения. Текст вложений
извлекается при синхронизации с лимитом размера. Каждый инструмент требует `connection`. Детали —
раздел 5.2, решения — раздел 10. Заодно зачёркнуты вопросы 1–3, решённые раньше. В разделе 8
остался только вопрос 14 — проверка Mail.ru в аккаунте, вместе с остальными проверками со входом
(раздел 9).
